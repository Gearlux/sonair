# Sonair Mandates

## Current state

Image classification on FOUR engines — standard Lightning, Keras 3, native TensorFlow and fastai — driven by one config. Modules — `lightning_classifier.py` (`LightningClassifier`, the merged train/evaluate/test/predict class), `timm_model.py` (`TimmModel`, default `efficientvit_b0`), `torch_classification.py` + `keras_classification.py` + `fastai_classification.py` (registered upstream losses/metrics, ONE MODULE PER LOSS API, no wrappers) — plus `cli.py` (`sonair <backend> train/evaluate/predict` — `lightning` / `keras` / `tensorflow` / `fastai` implemented from an `IMPLEMENTED` table + `_backend_app` factory, `jax` / `huggingface` / `mlx` as templates, all in that one file), `keras_classifier.py` + `keras_model.py` + `_keras.py` (the second backend), `tensorflow_classifier.py` + `_tensorflow.py` (the third — a `KerasClassifier` SUBCLASS), `fastai_classifier.py` (the fourth). Datasets are the generic `recordstream.sources.HuggingFaceSource`; batches are **record dicts** addressed by configured keys (`input_key="image"` / `target_key="class"`), collated by `recordstream.collate_records`, labels walked via `iter_key`, string targets encoded by `LabelMap.encode()` directly — **`encode_stream` was DELETED 2026-07-29**, along with `_resolve_class_names`, `_write_class_names`, `_load_pinned_label_map` and `_finalize_metrics`. The layering that replaced them: recordstream owns the label vocabulary and its file format (`LabelMap.encode` sets `Stream.class_names`; the free `class_names(train, val, test)` reads it back), marainer owns where run artifacts land and that they are logged (`save_class_names` / `load_class_names` / `write_metrics_sidecar` + `lightning.checkpoint_dir`), and sonair owns NEITHER. `_write_class_names` had hand-rolled a JSON format `LabelMap.save` already writes. Do not reintroduce a filesystem or vocabulary helper here; single- AND multi-label (`recordstream.MultiLabel`) targets are both supported, the loss/metric defaults resolving from the data in `initialize()`. Ctor knobs: `batch_size`/`num_workers`/`max_epochs`/`logger` (persistent workers derive from `num_workers` — there is no `persist_workers` knob). Example config: `examples/train_efficientvit_b0_mnist.yaml` — **it trains end to end** (3 epochs MNIST -> 99.5% top-1, verified 2026-07-29). **A classification config MUST carry an image pipeline:** the model is fed by `Stream(source=..., ops=!ref:preprocess)`, where `preprocess` is `ConvertToImage(width/height)` -> `!class:albumentations.Normalize` (the backbone's mean/std) -> `ToTensor(normalize=false)`. Three traps it encodes, each hit for real: (1) a bare `HuggingFaceSource` with no ops hands the model `[N, 28, 28]` and `TimmModel` rejects it — the source does NOT tensorize; (2) the nested source needs the INSTANCE form `!class:...HuggingFaceSource()` **with parens** — without them `Stream.source` stays a deferred Class marker and iteration raises (recordstream's guard names the fix); (3) `ToTensor`'s `normalize` MUST be `false` after an explicit Normalize — `to_tensor`'s heuristic divides any float whose max exceeds 1.0 by 255, so standardized pixels get squashed to ~[-0.01, 0.01] silently. Name `preprocess` once and `!ref:` it from both splits so train and eval cannot drift.

- **The Framework Is A CLI Dimension — `sonair <backend> <verb>` (2026-07-28):** sonair is the workspace DEMO that the config is the program, so the training backend is explicit in the command line. It all lives in `cli.py` — TWO tables plus two factories: `IMPLEMENTED: Dict[str, Backend]` (name -> description + the module whose import registers that engine's losses/metrics) built by `_backend_app`, and `TEMPLATES` built by `_template_app`. **The "written out plainly" arrangement was RETIRED 2026-07-30** when `tensorflow` and `fastai` landed as the third and fourth backends: the earlier mandate said explicitly "if a THIRD real backend lands, revisit then", and twelve near-identical handlers differing in exactly three values is what a table is for. There is still NO registry module / `Framework` dataclass — `Backend` is a two-field `NamedTuple` of DATA, and per-backend BEHAVIOUR stays out of it (see `_pin_keras_backend` below, which would have been a fifth column that is `None` three times out of four). Graduating a template = move its entry from `TEMPLATES` to `IMPLEMENTED` and add it to `EXPECTED_IMPLEMENTED` in `tests/test_cli_frameworks.py`, which then holds it to the same verb surface as the others. Handlers are built by a FACTORY (`_backend_command`), which also solves what the explicit `name=` used to: four module-level `def train` would collide. Rationale: `docs/architecture.md` §1a. Verbs map `train`/`evaluate`/`predict` -> `fit`/`test`/`predict`, the verb winning over the YAML's `task:`. **The verbs are `flow_mode="manual"` and build through `recordstream.cli.materialize_runnable` (2026-07-29) — NEVER a bare `flow()` / liquifai's `"auto"` deep-flow:** liquifai's DI only materializes a bound node against its document when the command param is annotated with a *configurable class*, and these annotate `runnable: Any` (the runnable is polymorphic), so an auto flow drops EVERY top-level key silently — `train_set` -> `None` (surfacing much later as `could not determine num_classes` after a 0-record target walk) and `max_epochs: 3` -> the ctor default (never surfacing at all). Rationale + the fallbacks: recordstream `AGENTS.md` -> the `recordstream.cli` mandate. Pins: `tests/test_cli_frameworks.py` (`test_dispatch_builds_with_the_flat_configs_top_level_keys` + the delegation spy). Template verbs EXIST (so `--help`/TAB advertise the roadmap), take NO `runnable` param (so they fail before liquifai resolves a config for a missing class), and raise `BackendNotImplementedError` (dual-inherits `LiquifaiError` + `NotImplementedError`, so liquifai renders one clean line + exit 1 instead of a traceback) naming the file to create and the block to replace. Build handlers with a FACTORY, never a default-argument closure — liquifai reads the signature, so smuggled loop variables would surface as `--_name` flags. Every template's name must match a pyproject extra (pinned). Gotcha (RESOLVED 2026-07-29): the message used to be `rich.markup.escape`d at the raise site because liquifai's failure handler interpolated the exception into a Rich markup string — unescaped, `sonair[keras]` lost its extra and printed a WRONG install command. **liquifai 0.1.1 escapes in its own renderer**, so the workaround is GONE; do not reintroduce it (double-escaping would print the literal backslashes). Verified by running `sonair keras train`. **One config, every backend:** the example config keeps engine-agnostic keys (dataset, knobs, run identity) at the TOP LEVEL — which is also the default backend — and each alternative is a `!scope:framework=<name>` block overriding ONLY the framework-specific keys (`runnable`/`model`/`logger`); confluid splices an active block into its parent in document order, last-write-wins. `main()` injects `--scope framework=<verb>` from the backend verb (`_inject_framework_scope`) so the backend is never named twice; an explicit `--scope framework=`/`--framework` always wins. Alternative blocks stay COMMENTED until their runnable class exists — a live block naming a missing class would break `tests/test_examples_load.py`, and until one is uncommented the config declares no `framework` dimension (so the injected scope is an inert no-op, pinned). **`sonair tensorflow` pins `KERAS_BACKEND` in `main()`, BEFORE liquifai resolves anything (2026-07-30):** `_pin_keras_backend(_selected_backend(sys.argv))` does `os.environ.setdefault("KERAS_BACKEND", "tensorflow")` for that verb only. It CANNOT live in the handler: liquifai resolves the config first, and a `!class:sonair.TensorFlowClassifier` tag imports the runnable — and therefore keras — during that resolution. `setdefault`, so an explicit choice still wins and is then REPORTED by `TensorFlowClassifier.initialize()` rather than silently overridden. Two further layers back it up; all three are in `docs/architecture.md` §6. **Losses/metrics/models/trainers are ENGINE-BOUND — every sonair registration declares `framework="torch"` (2026-07-29):** confluid 0.3.0 added `framework` as a third orthogonal discovery axis (`task`/`role` say what a class is FOR, `framework` says what it can be WIRED TO), so the losses + metrics, `TimmModel`, `LightningClassifier`, `KerasModel` and `KerasClassifier` all carry it and navigaitor's slot picker filters on it — a torch loss is no longer offered to a Keras trainer. Requires `confluid>=0.3.0` (passing the kwarg against 0.2.0 is a TypeError at import). **Each engine's registrations live in its OWN module** — `torch_classification.py` (`framework="torch"`) and `keras_classification.py` (`framework="keras"`), one entry point each, so a missing backend drops its whole set; a new backend adds a `<framework>_classification.py`, never a branch in an existing one. NOT yet enforced in StreamStudio — its object sockets are string-equality-matched by ComfyUI and persisted in saved workflows, so qualifying them is a breaking format change (see `TASKS.md`). Rationale: `docs/architecture.md` §2. Pins: `tests/test_cli_frameworks.py` (the CLI axis) + `tests/test_categories.py` (the framework tags). Docs: `docs/frameworks.md`, `docs/architecture.md`.
- **The Keras Backend Proves The Claim, And Reuses Everything (2026-07-29):** `KerasClassifier` (+ `KerasModel`) is the SECOND implemented backend, and its value is how little it contains: `_to_arrays` (eight lines saying what a classification batch looks like), `compile()`/`fit()`, and the task dispatch. Everything else is shared — the record stream, **the batching adapter**, `LabelMap` fitting/encoding, `class_names`, `ClassificationPredictionsSink`, `save_class_names` / `write_metrics_sidecar`, the `@entrypoint` dispatch, and the sentinel loss/metric defaults (same reasoning as the torch backend: a live default is indistinguishable from a user's choice). **`RecordSequence` MOVED to `recordstream.keras` (2026-07-30) — do not reintroduce a `PyDataset` subclass here.** It is the DataLoader half Keras leaves to the caller (row order, slicing, short final batch, per-epoch reshuffle, `collate_records`) and ~60% of it never mentioned classification, while its torch twin in `lightning_classifier.py` is one `LazyClass(DataLoader, collate_fn=collate_records)` line — the asymmetry was the tell. What stays here is the batch SHAPE, handed in through `transform=` exactly as a `collate_fn` is handed to a `DataLoader`: `_sequence()` wires `partial(self._to_arrays, with_targets=...)`, and `_to_arrays` is the twin of the Lightning backend's `_targets` (float32 `x` under `input_key`; `multi_hot` for a multi-label target, else int64 ids — int64 named EXPLICITLY, same reason as torch). Predict pairs output with metadata via `sequence.batches()` (recordstream's name; the old local method was `records()` and returned batches). **This is why `multi_hot` and `batch_values` return NUMPY** — a torch-typed return would have forced a second implementation here, and `ClassificationOutput` being generic in its array type is why ONE sink consumes both engines' output with no adapter. **Keras 3 reads `KERAS_BACKEND` at IMPORT time and defaults to `tensorflow`**, which sonair does not require — and that ordering ALSO moved down (2026-07-30): `recordstream.keras` does the `os.environ.setdefault` to the first INSTALLED backend, because import sorters put `from recordstream.keras import RecordSequence` ABOVE `from sonair._keras import keras`, so a sonair-side shim would have lost the race and reintroduced `ModuleNotFoundError: No module named 'tensorflow'`. `sonair/_keras.py` survives as the one-line re-export so every sonair module keeps ONE spelling — still never `import keras` directly. The keras names are LAZY in `sonair/__init__.py` (PEP 562) so a torch-only install never imports keras; `sonair[keras]` therefore declares `recordstream[keras]`. Keras's file-writing callbacks (`CSVLogger`/`ModelCheckpoint`) do NOT create their parent directory — `_callbacks()` does, because that failure otherwise lands minutes into a fit. **TWO real differences from the torch backend, both in the config's `preprocess` block and both about the ENGINE, not the task:** (1) Keras is channels-LAST, so the chain simply STOPS after `ConvertToImage` where torch adds `ToTensor` to transpose HWC->CHW; (2) `keras.applications` models carry their OWN preprocessing (`include_preprocessing=True`, expecting raw [0,255] pixels), so the Keras chain must NOT normalize — timm models do not preprocess, which is why the torch chain does it explicitly. Applying both is silent: the model simply trains worse. **`from_logits=True` is MANDATORY on the default losses (2026-07-29):** the head is a bare `Dense` with no activation (raw logits, matching torch's `CrossEntropyLoss`), but Keras's STRING losses default to `from_logits=False` — handed logits they normalize by the row SUM instead of a softmax and then CLIP rather than raise, so the loss stays finite and merely WRONG. A real MNIST run diverged to `loss: nan` with `val_accuracy: 0.098` (chance) before this was found; the corrected loss descends 1.72 -> 0.44 -> 0.13 on the same data. Never write the string form for a logit-emitting head. Pins: the `from_logits` group in `tests/test_keras_classifier.py`, including the head-emits-logits check that would catch a softmax being added later. **Verified end to end (2026-07-29):** the same example config reaches 99.52% top-1 under `lightning` and 99.18% best val under `keras`, changing only the verb. **`KerasModel` IS a `keras.Model` (2026-07-31)** — the mirroring goes down to the base class, since `TimmModel` IS an `nn.Module`. So `compile`/`fit`/`evaluate`/`predict`/`export`/`save`/`save_weights`/`trainable_variables` are INHERITED, not delegated, and the `network = getattr(self.model, "model", self.model)` that stood at three call sites across two backends is DELETED — it existed only because a bare `keras.Model` has no `.model` attribute (measured), i.e. a fallback in the CALLER standing in for a base class the wrapper lacked. Do not reintroduce it: a call site that seems to need it means the wrapper is missing a base class. Two members stay hand-written and BOTH are measured, not stylistic: **`build(input_shape)`** carries the lazy build because Keras forbids a built layer from adding sub-layers (creating the network in `call()` dies with *"You cannot add new elements of state … to a layer that is already built"* — hit for real), and `build()` runs before the first call, which is what keeps a never-flowed instance usable; **`output_shape`** is Functional-only and a subclassed model raises `AttributeError` for it. Consequences worth knowing: `_compile()` compiles the WIRED OBJECT, so `loss`/`_compile_metrics` read off `self.model` directly; `trained_model` returns the WRAPPER (a fix — it carries `num_classes`, which an evaluation run reads off its model slot, so the output now docks into a downstream classifier); and every call site is a plain `self.model.compile(...)` / `.fit(...)` / `.trainable_variables` with NO accessor in between. **That last part needed one annotation change, and it is the general rule (2026-07-31):** the `getattr` had been doubling as a TYPE escape hatch (`getattr` returns `Any`), so deleting it surfaced 14 mypy `union-attr` errors — `self.model: Lazy[Any]` is `Union[Any, Fluid]`, and mypy rejects a method call through the `Fluid` arm. The fix is NOT an accessor (a `_live_model()` helper was written and thrown away — it is the same "don't trust the code" reflex as the `isinstance` guards above): the ATTRIBUTE is annotated with the real type, `self.model: keras.Model = model`, while the CONSTRUCTOR param keeps `Mandatory[Lazy[Any]]` — which is the only place the marker is machine-read (`lazy_param_names(KerasClassifier)` still reports `model`, verified). Restating `Lazy` on the attribute bought nothing and cost every direct call. `warn_unreachable` is off in the root `mypy.ini`, so the `isinstance(self.model, Fluid)` in the `trained_model` `@output` still type-checks. Rationale: `docs/architecture.md` §7. Pins: `tests/test_keras_classifier.py` (the model-slot group, incl. a BARE `keras.Model` wired in the same slot and the never-flowed build path).
- **The TensorFlow Backend Is A `KerasClassifier` SUBCLASS, And Only The Loop Differs (2026-07-30):** `TensorFlowClassifier` answers the long-open `TASKS.md` question ("does `sonair tensorflow train` need its own runnable, when `KERAS_BACKEND=tensorflow sonair keras train` already runs the identical config?") with: YES, but ONLY for what Keras 3 does not expose. So it SUBCLASSES `KerasClassifier` and overrides sixteen names, every one about `tf.data`, the traced loop, or the SavedModel — `_dataset` (`tf.data.Dataset.from_generator` over the SAME `RecordSequence`, `.prefetch(tf.data.AUTOTUNE)`), `_train_step_fn`/`_eval_step_fn`/`_predict_step_fn` (`tf.GradientTape` under `@tf.function`, which is what makes `jit_compile`/XLA a knob), `_compile` (keeps the parent's NAME because `initialize()` calls it, replaces the BODY: a compiled model owns its own training step, which is exactly what this replaces), `_run_epoch`, `_export` (`keras.Model.export`, TF-only). Label handling, `num_classes` resolution, `_to_arrays`, the prediction contract and the artifacts are INHERITED, not copied — pinned by `test_it_overrides_only_the_tensorflow_specific_behaviour`, which fails if a classification concern drifts in (it belongs on the parent, where every backend gets it). It declares `framework="keras"`, NOT `"tensorflow"`: the axis names the API a class is WIRED TO (§2), and this one is wired to `keras.losses`/`keras.metrics`/`KerasModel`. **There is therefore NO `tensorflow_classification.py` and NO `TensorFlowModel`** — TF >= 2.16's `tf.keras` IS Keras 3, so a second loss module would register the same classes under a second tag and make every bare `!class:SparseCategoricalCrossentropy@role=loss` ambiguous; the CLI's `IMPLEMENTED["tensorflow"]` names `sonair.keras_classification` on purpose (pinned). The constructor RESTATES every parent parameter rather than taking `**kwargs` — `to_pydantic`/form-specs read the signature. **`_resolve_task_defaults` HAD to diverge:** the Keras backend defaults `metrics` to `["accuracy"]` because `compile()` resolves that alias CONTEXTUALLY (by loss + target shape); a hand-written loop has no `compile()`, and `keras.metrics.get("accuracy")` returns the elementwise-equality function, which reports `0.0` forever on a raw-logits head — so the defaults here are the concrete classes (`SparseCategoricalAccuracy` / `BinaryAccuracy(threshold=0.0)`) and `_as_metric` maps the alias the same way. Two things a `fit()` would have done for you and the loop must do itself: `sequence.on_epoch_end()` (the per-epoch reshuffle — forgetting it is INVISIBLE, training just runs on one fixed row order; pinned) and `optimizer.build(...)` BEFORE the `tf.function` (Keras builds slot variables on first `apply_gradients`, and creating variables during a RETRACE — which a short final batch triggers — is an error). Callbacks are driven by hand through a `keras.callbacks.CallbackList`, so `CSVLogger` and marainer's Keras tracking callback behave exactly as under `fit()`. **Verified end to end 2026-07-30:** `sonair tensorflow train` on a 256-row MNIST slice — loss 2.14 -> 0.98, accuracy 0.26 -> 0.73, CSV written, `saved_model.pb` + `variables/` exported. Rationale: `docs/architecture.md` §4. Pins: `tests/test_tensorflow_classifier.py`.
- **The fastai Backend Swaps The LOOP And Nothing Else (2026-07-30):** `FastaiClassifier` runs on torch, so it reuses `TimmModel` unchanged, the `[N, 3, H, W]` batch shape, `collate_records`, and the torch loss set — the `fastai` block in the example config overrides `runnable` and `logger` and NOTHING else, which is the smallest of the four and the project's strongest evidence for its own claim. What it owns: `_to_tuple` (the twin of the Lightning backend's `_targets` and the Keras backend's `_to_arrays` — fastai unpacks a batch POSITIONALLY, so the batch must BE a tuple rather than the record dict a `LightningModule` reads by key; int64 named explicitly, same reason as torch), `_dataloaders`, and the `Learner`. **The LOADERS are the Lightning backend's construction, not a private one (2026-07-31):** `train_loader` / `val_loader` / `test_loader` are `Lazy[DataLoader[Any]]` slots baked as `LazyClass(DataLoader, …)` in `__init__` with `batch_size`/`num_workers`/`persistent_workers`, flowed at run time with `dataset=` — same names, same deferral, same overridability, so ONE config idiom drives both backends and an operator can set `pin_memory` / `drop_last` / a sampler that the old inline `_loader()` helper made unreachable. The divergence is ONE kwarg: `collate_fn=self._to_tuple` where Lightning bakes `collate_records`. `predict()` reuses the SAME `test_loader` slot with a runtime `collate_fn=collate_records` override (a runtime kwarg wins over the stored one — measured) rather than owning a second loader, so the sink gets its record dicts while every other knob the operator set still applies. The private `_loader` / `_record_loader` / `_as_torch_dataset` helpers were DELETED with this — `_as_torch_dataset`'s own docstring had recorded the divergence ("the Lightning backend defers loader construction through a `LazyClass`; this backend builds the loader directly") instead of removing it. Likewise `_live_model()` is GONE: `self.model` is annotated `torch.nn.Module` (cast at the one assignment; the ctor param keeps `Mandatory[Lazy[Any]]`, which is where `lazy_param_names` reads the marker), so every use is a plain `self.model` / `self.model.eval()` — and the non-module check moved to the flow site in `initialize()`, where a wrong model fails during SETUP rather than minutes into a fit. Do not reintroduce a loader helper or a live-model accessor here. **`from fastai.callback import schedule  # noqa: F401` is load-bearing** — `Learner.fit_one_cycle` is a `@patch` installed as that module's IMPORT SIDE EFFECT, and fastai's `@patch` returns `None`, so `from fastai.callback.schedule import fit_one_cycle` binds None; without the import, `learn.fit_one_cycle` falls through fastcore's attribute delegation to the MODEL and raises `'TimmModel' object has no attribute 'fit_one_cycle'` (hit for real). So `_compile()` flows them at USE — the same thing `_callbacks()` already does for the `logger` slot — and BOTH spellings work; handed an unbuilt marker Keras takes it for a custom callable and fails deep inside `compile`. The slots are typed `Union[str, keras.losses.Loss]` etc. (never `Any`) for `to_pydantic`/form-spec, NOT for materialization. **Flow with a BARE `flow(value)` — never re-guard it with `isinstance(value, Fluid)` (2026-07-31):** `confluid.flow` opens with that idempotency check itself (`fluid.py` → `if not isinstance(obj, (Fluid, str, type, dict)): return obj`, and a non-tag string falls through to the closing `return obj`), so for every kind these slots admit — string alias, live instance, list, deferred marker — the guard was a no-op restating the callee. A private `_built()` helper wrapping it was DELETED workspace-wide on 2026-07-31 (it had spread to `keras_classifier` / `fastai_classifier` / `tensorflow_classifier`, the last two by copy); do not reintroduce it or the inline `flow(x) if isinstance(x, Fluid) else x` spelling. **The ONE case where the guard is load-bearing is a bare TYPE**, which `flow()` INSTANTIATES on the way past — and for a confluid-registered class it does so through `materialize()`, where sibling config keys broadcast into the constructor. Where a bare class is part of a helper's contract (`tensorflow_classifier._as_optimizer` / `_as_metric`, which accept "instance, class, or string alias"), test `isinstance(value, type)` BEFORE calling `flow`, not after. Genuine `isinstance(..., Fluid)` branches — ones that read `.target`/`.kwargs` off the marker (`lightning_classifier.accepts_class_weights`), pass runtime kwargs (`flow(self.loss_fn, weight=…)`), or raise on a still-deferred slot (the `trained_model` `@output`) — are unaffected. **The MODEL is flowed with NO guard at all — `self.model = flow(self.model, num_classes=self.num_classes)`, one unconditional line** in all three backends (`keras_classifier._compile`, `tensorflow_classifier._compile`, `fastai_classifier.initialize`). It reaches that line deferred because `!lazy:` is deliberately skipped by confluid's auto-flow walkers (`materialize` leaves a `Lazy` in place, measured) so the dataset-derived width can be injected at run time; an ALREADY-live model comes back as the identical object with the runtime kwarg DROPPED (measured), keeping the width its own constructor was given — which is what makes the call safe to run unconditionally. The line previously read `if isinstance(self.model, Fluid) or hasattr(self.model, "solidify"):`, whose second half admitted live models to a call that measurably does nothing (same object, kwarg dropped, `solidify()` never called) while reading as though the derived width were injected. Narrowing that to `isinstance(self.model, (Fluid, type))` was the same mistake one step smaller — a condition selecting exactly the cases the callee already selects. Delete such a condition; do not tighten it. Pins: the wiring group in `tests/test_keras_classification.py`; `tests/test_keras_classifier.py::test_a_live_model_is_left_exactly_as_it_arrived` + `::test_the_model_is_built_at_the_derived_width` for the two halves.
- **Collate Discipline — Wire the Generic `recordstream.collate_records` (record model, 2026-07-25):** `LightningClassifier` wires `recordstream.collate_records` as its DataLoader collate — there is NO bespoke sonair collate. The division of labour: (1) the **config pipeline tensorizes the input** (`ConvertToImage` → `ToTensor`), so at collate time each record's `input_key` value (default key `image`) is already a `[3, H, W]` `Image`; (2) `collate_records` **stacks** the `Image` value to `[N, 3, H, W]` and gathers plain entries as per-record lists; (3) the model boundary reads the batch back through recordstream's GENERIC readers — `batch_tensor(batch, key, device)` for the input and `batch_metadata(batch, exclude=(input_key, target_key))` for the per-record metadata a predictions sink needs (sonair's private `_batch_input`/`_batch_metadata` were DELETED 2026-07-29 and moved to `recordstream.batch`, where deltaid had an independent duplicate — do not reintroduce them); and the target comes from recordstream too — `_batch_target` was DELETED 2026-07-29 once `batch_tensor` grew a `dtype=` parameter and `multi_hot` moved down. What remains is `LightningClassifier._targets(batch)`, a two-branch CHOICE, not a shaper: `multi_hot(...)` -> `torch.as_tensor` for multi-label, else `batch_tensor(..., dtype=torch.int64)` — int64 named EXPLICITLY because a dataset yielding int32 label tensors is legal and `CrossEntropyLoss` rejects it (*"expected target dtype to be Long or Byte, but got Int"*); the old code relied on `LabelMap` happening to emit Python ints. Do not reintroduce a sonair-side shaper: if a new task shape is needed, it is a recordstream primitive plus a branch here. The record keys are CONFIG, not convention: `LightningClassifier(input_key="image", target_key="class")` (the `HuggingFaceSource` defaults). Don't reintroduce a sonair collate or move input-forcing back into the collate (resize / a model-keyed transform remains a pipeline concern).
- **`LightningClassifier` Resolves `num_classes` in `initialize()`:** The single `LightningClassifier` calls an explicit `initialize()` at the top of each `run()` entry point (NOT the auto-fired confluid `solidify` hook — so the dataset walk + model build happen at run time, not when a config is merely materialized). **A concrete (non-`Fluid`) model's classifier head is authoritative — its `num_classes` MUST be read from the model, never derived from a dataset walk that could mis-size the metrics against the head.** For **`task="fit"`** the resolution order is: a concrete model's `getattr(model, "num_classes")` → explicit `num_classes` ctor arg → the `label_map` (see below) → a lazy model's pinned `num_classes` kwarg → `recordstream.num_classes(train_set)` (walks integer targets, `max+1`); it then `flow(model, num_classes=…)` + flows the metric templates and clones per split. For **`task="evaluate"`/`"test"`/`"predict"`** it is **model-driven**: it flows/loads the model FIRST and reads `num_classes` straight off the LIVE model (`getattr(model, "num_classes")`) — the trained model's head is the single source of truth (NOT the eval dataset, which may be a subset and would mis-size the metrics; NOT the model's deferred `Fluid` kwargs, filled in later). It builds per-split metric collections through `marainer.lightning.build_metric_collection(metrics, num_classes=…)` (dict-of-templates → flow+wrap; ready-made `MetricCollection` → as-is) then clones per split (`train/`·`val/`·`test/` for fit; `val/` or `test/` for the eval tasks, idempotently). Use `recordstream.sources.HuggingFaceSource` as the dataset. Do NOT create specialized dataset wrappers in sonair, and do NOT reintroduce `marainer.dimensions` (removed) — flow the classes into instances directly.
- **String Targets Are Auto-Encoded via a `recordstream.LabelMap`; Imbalance Is Auto-Balanced:** `initialize()` peeks the FIRST target and asks recordstream's rule — `is_class_id(value)` — instead of sniffing types itself (the old `detect_target_kind` / `_target_to_int` are DELETED 2026-07-29; do not reintroduce them). Encoding goes through `LabelMap.to_ids`, which passes already-encoded ids through, so there is no name-vs-id branch left. A multi-label target is a `recordstream.MultiLabel` item (`iter_key` unwraps it to a LIST) — a sequence from the peek therefore IS multi-label, decided by the item type rather than by guessing what a list might mean. **Integer targets** flow through unchanged. **String (class-name) targets** are encoded to ids through a `recordstream.LabelMap` (the fittable companion to `EncodeTarget`): the pinned `label_map` ctor arg if given, else one **fitted from the train targets** (deterministic sorted-unique ordering, walked with a `tqdm` progress bar — sklearn was dropped from recordstream 2026-07-29). The wired `train`/`val`/`test` sets are then wrapped in a `recordstream.Stream` carrying `label_map.encode_op()`, and the map's `class_names` is exposed on the train set so marainer persists `class_names.json` — which the **evaluator reloads via `LabelMap.load`** (checkpoint-adjacent) so eval/predict share the identical name↔id ordering; **never refit on eval data**. When `balance_classes` is True (default) and `accepts_class_weights()` says the backend can take them, the SAME walked targets yield inverse-frequency class weights — computed by `recordstream.inverse_frequency_weights` (numpy) and injected by the `apply_class_weights` framework hook (exposed on `trainer.class_weights` as a Tensor). **`initialize()` walks the train targets AT MOST ONCE** ("Reading targets") and reuses that single pass for ALL of: fitting the encoder, deriving `num_classes` from the data, and computing balance weights — never walk the dataset twice (`_num_classes_without_data()` resolves the count from model/explicit/label_map/lazy-kwarg with no walk, and `_balance_loss` consumes the already-walked targets, never re-walking). The name→int map lives in **recordstream** (`LabelMap`, next to `EncodeTarget`/`DecodeTarget`), NOT sonair — it is a reusable primitive. **Multi-label targets are SUPPORTED (2026-07-29)** — a `MultiLabel` needs no config: `initialize()` sets `self.multilabel` from the peek and everything downstream follows from that ONE flag — `_batch_target(..., multilabel=True)` builds an `[N, C]` float multi-hot instead of `[N]` int64 ids, `_resolve_task_defaults()` picks `BCEWithLogitsLoss` + the `Multilabel*` metrics, `_metric_dims()` sizes them by `num_labels` instead of `num_classes`, and balancing flattens each record's ids through `LabelMap.to_ids` so a two-label record counts for both classes. Class-name strings encode exactly as in the single-label case (`LabelMap.fit` takes a `MultiLabel` directly). Do NOT add a `multilabel:` config knob — the target's item type already says it, and a knob could disagree with the data. Only the PREDICT-side sink is still single-label (top-k; see `TASKS.md`). Pins: the multi-label group in `tests/test_classification_trainer.py` (incl. an end-to-end `run()`).
- **`predict_step` Emits the CONTRACT, and `_write_predictions` Slices It Per Record (2026-07-29):** `predict_step` returns a `recordstream.ClassificationOutput` built by `recordstream.classification_output(logits)` — NOT the raw logits tensor. A predictions sink reads `probs` / `class_idx` by name and cannot softmax on the caller's behalf (only the model knows whether its head already did). Returning raw logits was a real defect: `recordstream.predictions.ClassificationPredictionsSink.write` does `prediction.get("probs")`, so a wired sink died with `AttributeError: 'Tensor' object has no attribute 'get'` on the first batch. `test_step` passes the same contract to the sink while its metrics still consume the raw logits. Separately, `_write_predictions` SLICES the batched output row-wise via `_per_record_predictions` — the sink contract is per-record while the model emits `[N, C]`, and the old list-wrapping wrote ONE entry for an N-record batch. `_per_record_predictions` handles, in order: a list (already per-record), a `{"predictions": [...]}` wrapper, a batched mapping with agreeing lengths (sliced), anything else (one prediction). Pins: `tests/test_predictions.py` (incl. an end-to-end pass through the real `recordstream.predictions` sink).
- **Task-Shaped Defaults Are SENTINELS, Resolved in `initialize()` (2026-07-29):** `loss_fn` and `metrics` default to **`None`** — meaning *not chosen*, never *no loss*. `_resolve_task_defaults()` fills an unset slot once `initialize()` knows `self.multilabel` (`BCEWithLogitsLoss` + `Multilabel*` vs `CrossEntropyLoss` + `Multiclass*`) and is idempotent, so an explicitly wired loss/metric is NEVER replaced. A live default in the constructor signature is prohibited: it makes "the user chose CrossEntropy" indistinguishable from "the user said nothing", so a multi-label run would either silently train with the wrong loss or silently discard a deliberate choice. Two ordering constraints, both already violated once: (1) resolution must run BEFORE the balancing probe in `_initialize_fit` — `loss_accepts_weight(None)` answers "cannot be balanced" and silently skips the target walk; (2) `training_step`/`validation_step` call `_resolve_task_defaults()` themselves so a directly-invoked step (tests, a custom loop) works without `initialize()`. Rationale: `docs/architecture.md` §3. Pins: `tests/test_classification_trainer.py` (`test_loss_fn_defaults_to_cross_entropy`, `test_an_explicitly_wired_loss_is_never_replaced`) + `tests/test_classification_evaluator.py`.
- **Deferred Slots Are Declared `Lazy[T]`, Never `Any` Or A Hand-Written Union (2026-07-29):** a slot this class flows ITSELF at run time — `model` (flowed with `num_classes=`), `train_set`/`test_set`, and the body slots `optimizer` (`params=`), `train_loader`/`val_loader`/`test_loader` (`dataset=`), `lightning` — MUST be annotated `Lazy[T]` (composed as `Mandatory[Lazy[T]]` where required). Two spellings are PROHIBITED: (a) `Optional[Union[X, Fluid]]`, which hand-writes confluid's alias — `Lazy = Annotated[Union[T, Fluid], _LAZY_MARKER]` — and silently drops the marker; (b) a bare `Any`, which type-checks nothing. What the marker buys differs by slot kind and the difference is REAL: for CONSTRUCTOR params it is machine-read (`confluid.lazy_param_names` reports them; liquifai's auto deep-flow SKIPS them instead of eagerly building a target that needs a runtime kwarg), while for BODY slots `lazy_param_names` scans `__init__` params only, so the marker is inert there and deferral is enforced by the slot holding a `LazyClass` value — the annotation still earns its place by giving `to_pydantic` a real type for navigaitor's form-spec / StreamStudio widgets. Before this landed, `lazy_param_names(<this class>)` returned an EMPTY set while the code flowed those very slots by hand. Dataset slots use the shared `marainer.torch.RecordSource` alias (`Dataset | Iterable[Record]` — the contract `ensure_record_dataset` enforces), never a locally-invented union. Pinned by `tests/test_lazy_slots.py`, which DERIVES the expectation from the source (every `flow(self.<slot>)` must be declared) rather than restating a list. `lazy_param_names` scans body slots as of confluid 2026-07-29, so the marker is machine-read on every slot here, not just the constructor ones.
