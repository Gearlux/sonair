# Sonair Mandates

- **Adapter, Not Classifier:** Sonair is a thin Confluid-`@configurable` wrapper around `timm`. Any of timm's ~1000 pretrained backbones MUST plug into the **unchanged** `marainer.trainer.LightningTrainer` step flow — no subclassing the Trainer, no overridden step functions, no custom Lightning module.
- **Per-Sample Predictions for Sinks:** `TimmClassifierForPrediction` MUST emit per-sample dict outputs (`{prediction, logits, ...}`) so marainer's `Evaluator.predictions_sink` can stream them downstream. Don't return a batched tensor where a per-sample mapping is expected.
- **Generic Primitives Live in Marainer / Waivefront / DataFlux — never Sonair:** Reusable predictions sinks do NOT belong in `sonair`. The modality-neutral `ClassificationPredictionsSink` lives in **`marainer`** (`marainer.sinks` — marainer owns the `predictions_sink` contract and the `ClassificationOutput` type it reads, and the sink has zero signal/image coupling); the signal-domain `DetectionPredictionsSink` (pixel→time/frequency back-projection) stays in `waivefront`. Classification needs NO bespoke target op at all — the input is tensorized by the generic `dataflux.ops.torch.ToTensorOp` (after `ConvertToImageOp`) and the label is encoded by the generic `dataflux.ops.target.MetadataToTargetOp` → `EncodeTargetOp` (the declarative scikit-`LabelEncoder` analogue). Sonair stays focused on the model + collate + trainer specialisation.
- **No Loss Wrapper — Register the Upstream Loss:** The classification loss IS `torch.nn.CrossEntropyLoss`; `sonair.classification` `register`s it (no wrapper class) as the `task="classification", role="loss"` configurable, so it's pickable in navigaitor's task surfaces and usable from YAML (`label_smoothing` / `ignore_index` / `reduction`). Don't reintroduce a sonair loss class. Per-class `weight` isn't expressible in YAML (it's a `Tensor`); a future weighted-loss need is met by registering another upstream loss or a generic shim, not by a sonair wrapper. (This is the model of the redesign: tag/register existing classes; navigaitor scans and generates — it invents nothing.)
- **Collate Discipline:** `classification_collate_fn` MUST preserve per-sample metadata alongside the batched input/target tensors so sinks can correlate predictions back to source samples.
- **Class Count Is a Lazy Method (the source of truth for `num_classes`):** `HuggingFaceClassificationDataset` exposes `num_classes()` as a **method** (never an `__init__`-time attribute) that walks the targets — target-only via dataflux's projection (`project()`), so no image is decoded — and returns `max(class_id)+1`. `derived_dimensions()` returns `{"num_classes": self.num_classes()}`; marainer reads this duck-typed and injects it when lazily constructing the model/metrics, so a training config may OMIT `num_classes` entirely. The dataset owns this logic and its description (navigaitor stays thin and surfaces it). Keep `label_names` (a cheap ClassLabel-feature read) for `class_names.json`, but do NOT resurrect an eager `num_classes` attribute — the walk is deliberately on-demand.
- **Backbone Knobs Pass-Through:** `TimmClassifierModel.__init__` MUST forward `model_name`, `num_classes`, `pretrained`, and any timm constructor knobs verbatim to `timm.create_model`. Don't shadow names; don't silently rewrite defaults.
- **Task/Role Discovery Tags:** Sonair's classes carry `@configurable(task="classification", role=...)` (which also derives the legacy `category="classification_<role>"`), so navigaitor's `list_classes(task=, role=)` scan + form-spec enumerate them: `TimmClassifierModel` → `role="model"`, `HuggingFaceClassificationDataset` → `role="dataset"`, `LightningClassificationTrainer` → `role="trainer"`, `LightningClassificationEvaluator` → `role="evaluator"`; the loss is `torch.nn.CrossEntropyLoss` `register`-ed as `role="loss"`. Preserve these when adding/renaming — `tests/test_categories.py` pins them, and a dropped tag silently empties the corresponding picker / drops the class from a generated task config.
