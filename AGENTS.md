# Sonair Mandates

## Current state

Image classification on standard Lightning. Three modules — `classifier.py` (`LightningClassifier`, the merged train/evaluate/test/predict class), `timm_classifier.py` (`TimmModel`, default `efficientvit_b0`), `classification.py` (registered upstream losses/metrics, no wrappers) — plus `cli.py` (`sonair train/evaluate/predict`). Datasets are the generic `sampleflux.sources.HuggingFaceSource`; batches are **record dicts** addressed by configured keys (`input_key="image"` / `target_key="class"`), collated by `sampleflux.collate_records`, labels walked via `iter_key`, string targets encoded by `LabelMap.encode_op()` (`EncodeTarget` — there is no `MetadataToTarget`). Ctor knobs: `batch_size`/`num_workers`/`max_epochs`/`logger` (persistent workers derive from `num_workers` — there is no `persist_workers` knob). Example config: `waivefront/config/train_efficientvit_b0_sonair.yaml`.

- **Standard Lightning Classifier + timm Models (2026-07 — supersedes "Adapter, Not Classifier"):** `sonair.classifier.LightningClassifier` is ONE self-contained standard `pytorch_lightning.LightningModule` — its OWN `training_step`/`validation_step`/`test_step`/`predict_step`/`configure_optimizers` + a `run()` that builds the loaders + `pl.Trainer` and dispatches on a `task` knob (`fit`/`evaluate`/`test`/`predict`, annotated via `sampleflux.runnable.entrypoint`). It replaces the old trainer+evaluator PAIR (both subclassed the deleted `marainer` bases). Marainer is now a tracking library — `LightningClassifier` uses it ONLY for optional tracking (`marainer.lightning.TrackingCallback` / `activate_for_lightning`) + torch utils (`marainer.torch.ensure_sample_dataset` / `build_metric_collection`); removing marainer needs only a few line changes. `TimmModel` stays a thin `@configurable` timm wrapper. Run via `sonair train/evaluate/predict cfg.yaml` or `sampleflux run cfg.yaml` (config roots at `runnable:` + `task:`).
- **Generic Primitives Live in Marainer / Waivefront / SampleFlux — never Sonair:** Reusable predictions sinks do NOT belong in `sonair`. The modality-neutral `ClassificationPredictionsSink` lives in **`marainer`** (`marainer.sinks` — marainer owns the `predictions_sink` contract and the `ClassificationOutput` type it reads, and the sink has zero signal/image coupling); the signal-domain `DetectionPredictionsSink` (pixel→time/frequency back-projection) stays in `waivefront`. Classification needs NO bespoke target op at all — the input is tensorized by the generic `sampleflux.ops.torch.ToTensor` (after `ConvertToImage`) and the label is encoded by the generic `sampleflux.ops.target.EncodeTarget` (the declarative scikit-`LabelEncoder` analogue, fitted and pinned through `sampleflux.LabelMap`). Sonair stays focused on the model + collate + trainer specialisation.
- **No Loss/Metric Wrappers — Register the Upstream Classes (`sonair.classification`):** Classification losses ARE off-the-shelf `torch.nn` losses and metrics ARE off-the-shelf `torchmetrics.classification` classes; `sonair.classification` `register`s them (no wrapper classes) — the losses (`_CLASSIFICATION_LOSSES`: `CrossEntropyLoss` / `BCELoss` / `BCEWithLogitsLoss` / `MultiLabelSoftMarginLoss` / `MultiMarginLoss` / `MultiLabelMarginLoss` / `SoftMarginLoss` / `HingeEmbeddingLoss`) as `task="classification", role="loss"`, the metrics (`_CLASSIFICATION_METRICS`: the `Multiclass*` family — `MulticlassAccuracy`/`F1Score`/`Precision`/`Recall`/`AUROC`/`AveragePrecision`/`Specificity`/`CohenKappa`/`MatthewsCorrCoef`/`ConfusionMatrix`/`JaccardIndex`/`CalibrationError`/`HammingDistance`) as `task="classification", role="metric"`. Each is pickable in navigaitor's task surfaces, usable from YAML, AND a FluxStudio OBJECT node (`role∈{loss,metric}` is in the bridge `_MEMBER_ROLES`). **They surface in FluxStudio ONLY because `sonair.classification` is its own `confluid.configurables` entry point** (`sonair-classification = "sonair.classification"`) AND every registered class is named in the module's literal `__all__` — `scan_module` filters by `__module__` (which is `torch`/`torchmetrics` for these), so the `__all__`-gated discovery pass is what picks them up. When you add a loss/metric: append it to the right `_CLASSIFICATION_*` tuple AND to `__all__` (`tests/test_categories.py` pins the sync); after changing the set, reinstall the editable (`uv pip install -e ./sonair --no-deps`, or `aisland setup`) so the entry-point metadata refreshes, then restart ComfyUI. Don't reintroduce a sonair loss/metric class that *reimplements* one. Per-class `weight` isn't expressible in YAML (it's a `Tensor`); a future weighted-loss need is met by registering another upstream loss or a generic shim, not by a bespoke sonair wrapper. (This is the model of the redesign: tag/register existing classes; navigaitor scans and generates — it invents nothing.) **The one allowed exception is the "generic shim":** when the upstream loss is a plain *function* rather than an `nn.Module` (so confluid's `register`, which only tags classes, can't reach it), a minimal `nn.Module` wrapper that just stores knobs and delegates in `forward` is permitted — this is a transport shim, not a reimplementation. The reference is `SigmoidFocalLoss` (wrapping `torchvision.ops.sigmoid_focal_loss`): it adds no math, satisfies the zero-arg / lazy-init mandate (ctor only stores `alpha`/`gamma`/`reduction`), and is `@configurable(task="classification", role="loss")`. Like the multi-label family it consumes **float** targets shaped like the logits (one-hot `[N, C]`), not int64 class ids.
- **Collate Discipline — Wire the Generic `sampleflux.collate_records` (record model, 2026-07-25):** `LightningClassifier` wires `sampleflux.collate_records` as its DataLoader collate — there is NO bespoke sonair collate. The division of labour: (1) the **config pipeline tensorizes the input** (`ConvertToImage` → `ToTensor`), so at collate time each record's `input_key` value (default key `image`) is already a `[3, H, W]` `Image`; (2) `collate_records` **stacks** the `Image` value to `[N, 3, H, W]` and gathers plain entries as per-record lists; (3) the model boundary in `sonair.classifier` unwraps the batched input (`_batch_input(batch, key)`), **stacks the `Label` target's per-record list into an `[N]` int64 tensor** (`_batch_target` — the one thing `collate_records` does NOT do for a wrapper-item target), and transposes the remaining keys into a per-record metadata list (`_batch_metadata`) for prediction sinks. The record keys are CONFIG, not convention: `LightningClassifier(input_key="image", target_key="class")` (the `HuggingFaceSource` defaults). Don't reintroduce a sonair collate or move input-forcing back into the collate (resize / a model-keyed transform remains a pipeline concern).
- **`LightningClassifier` Resolves `num_classes` in `initialize()`:** The single `LightningClassifier` calls an explicit `initialize()` at the top of each `run()` entry point (NOT the auto-fired confluid `solidify` hook — so the dataset walk + model build happen at run time, not when a config is merely materialized). **A concrete (non-`Fluid`) model's classifier head is authoritative — its `num_classes` MUST be read from the model, never derived from a dataset walk that could mis-size the metrics against the head.** For **`task="fit"`** the resolution order is: a concrete model's `getattr(model, "num_classes")` → explicit `num_classes` ctor arg → the `label_map` (see below) → a lazy model's pinned `num_classes` kwarg → `sampleflux.num_classes(train_set)` (walks integer targets, `max+1`); it then `flow(model, num_classes=…)` + flows the metric templates and clones per split. For **`task="evaluate"`/`"test"`/`"predict"`** it is **model-driven**: it flows/loads the model FIRST and reads `num_classes` straight off the LIVE model (`getattr(model, "num_classes")`) — the trained model's head is the single source of truth (NOT the eval dataset, which may be a subset and would mis-size the metrics; NOT the model's deferred `Fluid` kwargs, filled in later). It builds per-split metric collections through `marainer.lightning.build_metric_collection(metrics, num_classes=…)` (dict-of-templates → flow+wrap; ready-made `MetricCollection` → as-is) then clones per split (`train/`·`val/`·`test/` for fit; `val/` or `test/` for the eval tasks, idempotently). Use `sampleflux.sources.HuggingFaceSource` as the dataset. Do NOT create specialized dataset wrappers in sonair, and do NOT reintroduce `marainer.dimensions` (removed) — flow the classes into instances directly.
- **String Targets Are Auto-Encoded via a `sampleflux.LabelMap`; Imbalance Is Auto-Balanced:** `initialize()` peeks the target kind. **Integer targets** flow through unchanged. **String (class-name) targets** are encoded to ids through a `sampleflux.LabelMap` (the fittable companion to `EncodeTarget`): the pinned `label_map` ctor arg if given, else one **fitted from the train targets** (sklearn `LabelEncoder`, walked with a `tqdm` progress bar). The wired `train`/`val`/`test` sets are then wrapped in a `sampleflux.Flux` carrying `label_map.encode_op()`, and the map's `label_names` is exposed on the train set so marainer persists `class_names.json` — which the **evaluator reloads via `LabelMap.load`** (checkpoint-adjacent) so eval/predict share the identical name↔id ordering; **never refit on eval data**. When `balance_classes` is True (default) and the loss accepts a `weight` tensor, the walked targets also yield inverse-frequency class weights injected into `loss_fn` (exposed on `trainer.class_weights`). **`initialize()` walks the train targets AT MOST ONCE** ("Reading targets") and reuses that single pass for ALL of: fitting the encoder, deriving `num_classes` from the data, and computing balance weights — never walk the dataset twice (`_num_classes_without_data()` resolves the count from model/explicit/label_map/lazy-kwarg with no walk, and `_apply_class_weights` consumes the already-walked targets, never re-walking). The name→int map lives in **sampleflux** (`LabelMap`, next to `EncodeTarget`/`DecodeTarget`), NOT sonair — it is a reusable primitive. **Multi-label string targets** (a sequence of names) raise `NotImplementedError` (multi-hot + BCE + collate changes are a TASKS.md follow-up).
- **Backbone Knobs Pass-Through:** `TimmModel.__init__` MUST forward `model_name`, `num_classes`, `pretrained`, and any timm constructor knobs verbatim to `timm.create_model`. Don't shadow names; don't silently rewrite defaults.
- **Lazy Backbone — One Cache, Three Triggers (`solidify` / `backbone` / `forward`):** `TimmModel.__init__` does NO functional work (Lazy-Init / Zero-Arg mandate); the timm backbone is built lazily into the **public** submodule `self.classifier` (public name, NOT `_classifier`, so a state_dict round-trips as `classifier.*` through marainer's Lightning checkpoint loader). It builds at most once, triggered by any of: `solidify()` (the build+cache method), the read-only cached `@property backbone` (which just returns `solidify()`), or `forward()` (which routes through `backbone`). **Keep `solidify()` — it's confluid's `flow()`-time build hook** (`flow` never touches `@property` getters — confluid AGENTS rule 3 — so the method hook is what leaves `self.parameters()` ready before `configure_optimizers`, and it's what fires the dual-output FluxStudio node's build-or-warn at node-execute). The `backbone` property is the ergonomic accessor so a **directly-constructed, never-flowed** `TimmModel` still materializes on demand (`model.backbone(x)`). Required config (`model_name` / `num_classes`, sentinels `""`/`0`) is validated at build time with a clear error, never in `__init__`. Do NOT move the build into `__init__` (breaks zero-arg construction) and do NOT drop `solidify()` (breaks flow-time build + the node warning). Pins: `tests/test_timm_classifier.py` (`backbone` property + solidify + checkpoint round-trip).
- **Ergonomic Flat Config via Broadcasting:** `LightningClassifier` exposes ergonomic ctor knobs — `batch_size` / `num_workers` / `max_epochs` / `logger` — so a **flat** YAML drives it purely through Confluid broadcasting (top-level sibling keys inject into the same-named ctor params — no nesting / `!ref`). `batch_size` / `num_workers` are baked into the deferred `DataLoader` stubs (with `sampleflux.collate_records`) in `__init__`; `max_epochs` / `logger` are baked into the classifier's OWN `self.lightning = LazyClass(pytorch_lightning.Trainer, max_epochs=…, logger=…)` (there is NO base trainer anymore) — `_build_trainer()`'s `flow(self.lightning)` at run() then materializes any `!class:` logger Fluids in that list. The model is wired `!lazy:sonair.TimmModel` (no `num_classes`); `initialize()` flows it with the dataset-derived count at run time. Gotcha (pinned by `tests/test_classification_trainer.py`): a **list-valued** top-level key (`logger: [...]`) only broadcasts when the receiving param's annotation admits a list — confluid's `_classify_annotation` gates list/dict broadcast on the annotation, so keep `logger` annotated `Optional[Union[Logger, Iterable[Logger], bool]]`. Passing an explicit `train_loader`/`val_loader`/`lightning` overrides the knob-built defaults. Use `pytorch_lightning.loggers.TensorBoardLogger` in flat configs.
- **Task/Role Discovery Tags:** Sonair's classes carry `@configurable(task="classification", role=...)` (which also derives the legacy `category="classification_<role>"`), so navigaitor's `list_classes(task=, role=)` scan + form-spec enumerate them: `TimmModel` → `role="model"`, `LightningClassifier` → `role="trainer"` (its per-task `run()` entry points additionally declare `trainer`/`evaluator`/`predictor` roles via `sampleflux.runnable.entrypoint`); the losses (the registered `torch.nn` family) are `role="loss"` and the metrics (the registered `torchmetrics.classification.Multiclass*` family) are `role="metric"` (see the loss/metric mandate above). Preserve these when adding/renaming — `tests/test_categories.py` pins them, and a dropped tag silently empties the corresponding picker / drops the class from a generated task config.
- **I/O Contract — `trained_model` Output + `Mandatory[...]` Inputs:** `LightningClassifier` declares its confluid I/O contract (the surface FluxStudio / navigaitor read — see confluid's *I/O Contract* mandate). Its constructor input `model` is typed `Mandatory[...]` (the explicit "must be wired" marker, distinct from the defaulted/`Optional` knobs like `train_set`/`test_set`); it declares **three read-only `@output`s DIRECTLY on the class** (not inherited — the old marainer bases are gone): `trained_model` — a read-only `@output` returning the live trained `nn.Module` (`self.model` after `run()`/`initialize()` flowed and trained it) — plus `computed_metrics` (`Dict[str, float]`, final scalar metrics) and `label_names` (`List[str]`). `trained_model` is NOT the `model` *input* (that's the `!lazy:` arch spec) and is NOT a config knob (read-only ⇒ excluded from `to_pydantic`); all three **raise** if accessed while the run hasn't happened (the model still a deferred `Fluid`), so they are run OUTPUTs only. `@output` goes UNDER `@property`. FluxStudio surfaces them as wireable output sockets on the self-running classifier node — `trained_model` on a `SAMPLEFLUX_OBJECT:model` socket (docking into a downstream `task: test` classifier's `model` slot), `computed_metrics`/`label_names` on `STRING` (JSON) sockets; navigaitor's form-spec surfaces them under `outputs`. Pins: `tests/test_classification_trainer.py` + `tests/test_classification_evaluator.py` (the `trained_model` / mandatory-input / `computed_metrics` / `label_names` output tests).
