# Sonair Mandates

## Current state

Image classification on EIGHT engines — standard Lightning, Keras 3, native TensorFlow and fastai — driven by one config. Modules — `lightning_classifier.py` (`LightningClassifier`, the merged train/evaluate/test/predict class), `timm_model.py` (`TimmModel`, default `efficientvit_b0`), `torch_classification.py` + `keras_classification.py` + `fastai_classification.py` (registered upstream losses/metrics, ONE MODULE PER LOSS API, no wrappers) — plus `cli.py` (`sonair <backend> train/evaluate/predict` — `lightning` / `keras` / `tensorflow` / `fastai` implemented from an `IMPLEMENTED` table + `_backend_app` factory, `jax` / `huggingface` / `mlx` as templates, all in that one file), `keras_classifier.py` + `keras_model.py` + `convnet/keras_convnet.py` + `_keras.py` (the second backend), `tensorflow_classifier.py` + `tensorflow_model.py` + `convnet/tensorflow_convnet.py` + `_tensorflow.py` (the third — a `KerasClassifier` SUBCLASS), `fastai_classifier.py` (the fourth), and the `convnet/` PACKAGE (`spec.py` plus its FIVE native implementations `torch_convnet.py`/`keras_convnet.py`/`tensorflow_convnet.py`/`flax_convnet.py`/`mlx_convnet.py`, each an instance of its framework's own module type — see the convnet-package mandate). Datasets are the generic `recordstream.sources.huggingface.HuggingFaceSource`; batches are **record dicts** addressed by configured keys (`input_key="image"` / `target_key="class"`), collated by `recordstream.collate_records`, labels walked via `iter_key`, string targets encoded by `LabelMap.encode()` directly — **`encode_stream` was DELETED 2026-07-29**, along with `_resolve_class_names`, `_write_class_names`, `_load_pinned_label_map` and `_finalize_metrics`. The layering that replaced them: recordstream owns the label vocabulary and its file format (`LabelMap.encode` sets `Stream.class_names`; the free `class_names(train, val, test)` reads it back), marainer owns where run artifacts land and that they are logged (`save_class_names` / `load_class_names` / `write_metrics_sidecar` + `lightning.checkpoint_dir`), and sonair owns NEITHER. `_write_class_names` had hand-rolled a JSON format `LabelMap.save` already writes. Do not reintroduce a filesystem or vocabulary helper here; single- AND multi-label (`recordstream.MultiLabel`) targets are both supported, the loss/metric defaults resolving from the data in `initialize()`. Ctor knobs: `batch_size`/`num_workers`/`max_epochs`/`logger` (persistent workers derive from `num_workers` — there is no `persist_workers` knob). Example config: `examples/train_efficientvit_b0_mnist.yaml` — **it trains end to end** (3 epochs MNIST -> 99.5% top-1, verified 2026-07-29). **A classification config MUST carry an image pipeline:** the model is fed by `Stream(source=..., ops=!ref:preprocess)`, where `preprocess` is `ConvertToImage(width/height)` -> `!class:albumentations.Normalize` (the backbone's mean/std) -> `ToTensor(normalize=false)`. Three traps it encodes, each hit for real: (1) a bare `HuggingFaceSource` with no ops hands the model `[N, 28, 28]` and `TimmModel` rejects it — the source does NOT tensorize; (2) the nested source needs the INSTANCE form `!class:...HuggingFaceSource()` **with parens** — without them `Stream.source` stays a deferred Class marker and iteration raises (recordstream's guard names the fix); (3) `ToTensor`'s `normalize` MUST be `false` after an explicit Normalize — `to_tensor`'s heuristic divides any float whose max exceeds 1.0 by 255, so standardized pixels get squashed to ~[-0.01, 0.01] silently. Name `preprocess` once and `!ref:` it from both splits so train and eval cannot drift.

- **The Framework Is A CONFIG Dimension The CLI Passes Through — `sonair <verb> cfg.yaml --framework <name>` (2026-08-01, supersedes the 2026-07-28 `sonair <backend> <verb>` mandate):** sonair is the workspace DEMO that the config is the program, so the training backend is named on the command line — but as a FLAG, because it is a property of the config and not of the CLI. `cli.py` holds THREE verbs (`train`/`evaluate`/`predict`, mapping to `fit`/`test`/`predict`, the verb winning over the YAML's `task:`), a `frameworks` listing command, and ONE table: `FRAMEWORKS: Dict[str, Framework]` (name -> description + the module whose import registers that engine's losses/metrics, or `None`). **The eight backend SUB-APPS were RETIRED**, and the reason is a property of the code rather than taste: a backend verb never SELECTED anything — `_inject_framework_scope` appended `--scope framework=<backend>` to `sys.argv` and the config's scope block did the work — so (a) nothing compared the verb against the config, and `sonair keras train <a config with no keras block>` trained the DEFAULT backend SILENTLY (measured), and (b) 24 commands differed in exactly two values. liquifai already binds `--KEY VAL` for any dimension a config declares (`flags.bind_dimension_flags`), so `recordstream run cfg.yaml --framework keras` worked before any of this was written. Do NOT reintroduce a backend subcommand, a `TEMPLATES` dict, `_backend_app`, `_template_app` or `BackendNotImplementedError` — an unbuilt backend is simply absent from `FRAMEWORKS`, and there is nowhere for a stub to hang once the backend is a flag. Rationale: `docs/architecture.md` §1b. **`--framework` is REWRITTEN to `--scope framework=<name>` in `main()` (`_normalize_framework_flag`), never appended:** liquifai binds the ergonomic flag only for dimensions the config DECLARES, so against a config with no `!scope:framework=…` block a bare `--framework keras` would be read as a config OVERRIDE and try to set a `framework` attribute; rewriting makes the flag mean one thing either way, and an undeclared dimension stays the inert no-op that lets a config grow into a backend it does not have yet. **The two pre-load steps read `argv` and MUST stay in `main()`** — `_pin_keras_backend` (see the KERAS_BACKEND mandate) and `_register_classification`, which imports the named framework's loss/metric module BEFORE `app.run()` because the EAGER instance form (`!class:Foo()` with parens) is built during config load, earlier than any handler runs. With NO `--framework` it imports NOTHING and that is deliberate: there is no safe guess (importing the default's set would drag torch into a keras-only install), and the failure mode is a LOUD `UnknownClassError` on a bare registered name, not a wrong result. It is best-effort on `ImportError` — a partial install is normal and its absent registrations are correct. **The verbs are `flow_mode="manual"` and build through `recordstream.cli.materialize_runnable` (2026-07-29) — NEVER a bare `flow()` / liquifai's `"auto"` deep-flow:** liquifai's DI only materializes a bound node against its document when the command param is annotated with a *configurable class*, and these annotate `runnable: Any` (the runnable is polymorphic), so an auto flow drops EVERY top-level key silently — `train_set` -> `None` (surfacing much later as `could not determine num_classes` after a 0-record target walk) and `max_epochs: 3` -> the ctor default (never surfacing at all). Rationale + the fallbacks: recordstream `AGENTS.md` -> the `recordstream.cli` mandate. Handlers are built by a FACTORY (`_verb_command`), never a default-argument closure — liquifai reads the signature, so a smuggled loop variable would surface as a `--_verb` flag. **One config, every backend, and EVERY framework-specific key is a TOP-LEVEL SIBLING** — `runnable`, `model`, `logger` — with each alternative a `!scope:framework=<name>` block overriding the ones it must; confluid splices an active block into its parent in document order, last-write-wins. The flatness is load-bearing, not cosmetic: a scope block replaces a KEY and takes its whole subtree, so the `model:` that used to be nested inside `runnable:` VANISHED the moment a block swapped the runnable — `sonair train examples/train_efficientvit_b0_mnist.yaml --framework torch` (the command printed in that file's own comments) died with `TorchClassifier.__init__() missing 1 required positional argument: 'model'` while the comment beside it claimed the model was inherited, and `fastai` had the same hole. Pinned by `tests/test_cli_frameworks.py::test_every_declared_framework_resolves_to_a_complete_runnable`, which is CONFIG-level so it fails on the machine that introduces the mistake rather than only where the extra happens to be installed. **The DEFAULT backend gets a block of its own** (`lightning: !scope:framework=lightning`, restating the runnable): the top level already IS lightning, but confluid 0.3.0 raises on an activation matching no block, so an undeclared default would make naming it explicitly an error. That raise is the check the verb could never do — a typo'd `--framework kears` is now an error listing the backends the config declares, where it used to fall through to the default. Requires `confluid>=0.3.0`. **Losses/metrics/models/trainers are ENGINE-BOUND — every sonair registration declares `framework="torch"` (2026-07-29):** confluid 0.3.0 added `framework` as a third orthogonal discovery axis (`task`/`role` say what a class is FOR, `framework` says what it can be WIRED TO), so the losses + metrics, `TimmModel`, `LightningClassifier`, `KerasModel` and `KerasClassifier` all carry it and navigaitor's slot picker filters on it — a torch loss is no longer offered to a Keras trainer. **Each engine's registrations live in its OWN module** — `torch_classification.py` (`framework="torch"`) and `keras_classification.py` (`framework="keras"`), one entry point each, so a missing backend drops its whole set; a new backend adds a `<framework>_classification.py`, never a branch in an existing one. NOT yet enforced in StreamStudio — its object sockets are string-equality-matched by ComfyUI and persisted in saved workflows, so qualifying them is a breaking format change (see `TASKS.md`). Rationale: `docs/architecture.md` §2. Pins: `tests/test_cli_frameworks.py` (the CLI axis, 55 cases) + `tests/test_categories.py` (the framework tags). Docs: `docs/frameworks.md`, `docs/architecture.md`.
- **The Keras Backend Proves The Claim, And Reuses Everything (2026-07-29):** `KerasClassifier` (+ `KerasModel`) is the SECOND implemented backend, and its value is how little it contains: `_to_arrays` (eight lines saying what a classification batch looks like), `compile()`/`fit()`, and the task dispatch. Everything else is shared — the record stream, **the batching adapter**, `LabelMap` fitting/encoding, `class_names`, `ClassificationPredictionsSink`, `save_class_names` / `write_metrics_sidecar`, the `@entrypoint` dispatch, and the sentinel loss/metric defaults (same reasoning as the torch backend: a live default is indistinguishable from a user's choice). **`RecordSequence` MOVED to `recordstream.keras` (2026-07-30) — do not reintroduce a `PyDataset` subclass here.** It is the DataLoader half Keras leaves to the caller (row order, slicing, short final batch, per-epoch reshuffle, `collate_records`) and ~60% of it never mentioned classification, while its torch twin in `lightning_classifier.py` is one `LazyClass(DataLoader, collate_fn=collate_records)` line — the asymmetry was the tell. What stays here is the batch SHAPE, handed in through `transform=` exactly as a `collate_fn` is handed to a `DataLoader`: `_sequence()` wires `partial(self._to_arrays, with_targets=...)`, and `_to_arrays` is the twin of the Lightning backend's `_targets` (float32 `x` under `input_key`; `multi_hot` for a multi-label target, else int64 ids — int64 named EXPLICITLY, same reason as torch). Predict pairs output with metadata via `sequence.batches()` (recordstream's name; the old local method was `records()` and returned batches). **This is why `multi_hot` and `batch_values` return NUMPY** — a torch-typed return would have forced a second implementation here, and `ClassificationOutput` being generic in its array type is why ONE sink consumes both engines' output with no adapter. **Keras 3 reads `KERAS_BACKEND` at IMPORT time and defaults to `tensorflow`**, which sonair does not require — and that ordering ALSO moved down (2026-07-30): `recordstream.keras` does the `os.environ.setdefault` to the first INSTALLED backend, because import sorters put `from recordstream.keras import RecordSequence` ABOVE `from sonair._keras import keras`, so a sonair-side shim would have lost the race and reintroduced `ModuleNotFoundError: No module named 'tensorflow'`. `sonair/_keras.py` survives as the one-line re-export so every sonair module keeps ONE spelling — still never `import keras` directly. The keras names are LAZY in `sonair/__init__.py` (PEP 562) so a torch-only install never imports keras; `sonair[keras]` therefore declares `recordstream[keras]`. Keras's file-writing callbacks (`CSVLogger`/`ModelCheckpoint`) do NOT create their parent directory — `_callbacks()` does, because that failure otherwise lands minutes into a fit. **TWO real differences from the torch backend, both in the config's `preprocess` block and both about the ENGINE, not the task:** (1) Keras is channels-LAST, so the chain simply STOPS after `ConvertToImage` where torch adds `ToTensor` to transpose HWC->CHW; (2) `keras.applications` models carry their OWN preprocessing (`include_preprocessing=True`, expecting raw [0,255] pixels), so the Keras chain must NOT normalize — timm models do not preprocess, which is why the torch chain does it explicitly. Applying both is silent: the model simply trains worse. **`from_logits=True` is MANDATORY on the default losses (2026-07-29):** the head is a bare `Dense` with no activation (raw logits, matching torch's `CrossEntropyLoss`), but Keras's STRING losses default to `from_logits=False` — handed logits they normalize by the row SUM instead of a softmax and then CLIP rather than raise, so the loss stays finite and merely WRONG. A real MNIST run diverged to `loss: nan` with `val_accuracy: 0.098` (chance) before this was found; the corrected loss descends 1.72 -> 0.44 -> 0.13 on the same data. Never write the string form for a logit-emitting head. Pins: the `from_logits` group in `tests/test_keras_classifier.py`, including the head-emits-logits check that would catch a softmax being added later. **Verified end to end (2026-07-29):** the same example config reaches 99.52% top-1 under `lightning` and 99.18% best val under `keras`, changing only the verb. **`KerasModel` IS a `keras.Model` (2026-07-31)** — the mirroring goes down to the base class, since `TimmModel` IS an `nn.Module`. So `compile`/`fit`/`evaluate`/`predict`/`export`/`save`/`save_weights`/`trainable_variables` are INHERITED, not delegated, and the `network = getattr(self.model, "model", self.model)` that stood at three call sites across two backends is DELETED — it existed only because a bare `keras.Model` has no `.model` attribute (measured), i.e. a fallback in the CALLER standing in for a base class the wrapper lacked. Do not reintroduce it: a call site that seems to need it means the wrapper is missing a base class. Two members stay hand-written and BOTH are measured, not stylistic: **`build(input_shape)`** carries the lazy build because Keras forbids a built layer from adding sub-layers (creating the network in `call()` dies with *"You cannot add new elements of state … to a layer that is already built"* — hit for real), and `build()` runs before the first call, which is what keeps a never-flowed instance usable; **`output_shape`** is Functional-only and a subclassed model raises `AttributeError` for it. Consequences worth knowing: `_compile()` compiles the WIRED OBJECT, so `loss`/`_compile_metrics` read off `self.model` directly; `trained_model` returns the WRAPPER (a fix — it carries `num_classes`, which an evaluation run reads off its model slot, so the output now docks into a downstream classifier); and every call site is a plain `self.model.compile(...)` / `.fit(...)` / `.trainable_variables` with NO accessor in between. **That last part needed one annotation change, and it is the general rule (2026-07-31):** the `getattr` had been doubling as a TYPE escape hatch (`getattr` returns `Any`), so deleting it surfaced 14 mypy `union-attr` errors — `self.model: Lazy[Any]` is `Union[Any, Fluid]`, and mypy rejects a method call through the `Fluid` arm. The fix is NOT an accessor (a `_live_model()` helper was written and thrown away — it is the same "don't trust the code" reflex as the `isinstance` guards above): the ATTRIBUTE is annotated with the real type, `self.model: keras.Model = model`, while the CONSTRUCTOR param keeps the `Lazy[...]` marker — the only place it is machine-read (`lazy_param_names(KerasClassifier)` still reports `model`, verified). That param read `Mandatory[Lazy[Any]]` until 2026-08-01 and is now `Mandatory[Lazy[keras.Model]]` — see the `Lazy[Any]`-is-half-a-declaration clause in the deferred-slots mandate. Restating `Lazy` on the attribute bought nothing and cost every direct call. `warn_unreachable` is off in the root `mypy.ini`, so the `isinstance(self.model, Fluid)` in the `trained_model` `@output` still type-checks. Rationale: `docs/architecture.md` §7. Pins: `tests/test_keras_classifier.py` (the model-slot group, incl. a BARE `keras.Model` wired in the same slot and the never-flowed build path).
- **The Bare-Torch Backend Is The CONTROL EXPERIMENT — `TorchClassifier`, no training framework at all (2026-08-01):** the EIGHTH backend and the only one with nothing underneath it: `zero_grad`/`backward`/`step` written out, an explicit device, an explicit `model.train()`/`model.eval()`, an explicit `torch.no_grad()` on the eval pass. **Why it earns its place in a project whose claim is that the config is the program:** every other backend says "swap the runnable, keep the config"; this one removes the training FRAMEWORK and the config still does not change — same `TimmModel`, same `preprocess` chain, same `torch.nn` losses (`sonair.torch_classification`, shared with `lightning` — `IMPLEMENTED["torch"].registrations` points at it deliberately, a loss does not care which loop calls it), same torchmetrics, same artifacts. A knob that only worked because Lightning implemented it shows up HERE. Its `!scope:framework=torch` block in the example config is the smallest in the file, which is the point. **What it does NOT have, and why that is honest rather than missing:** no `logger:` slot (those are `pytorch_lightning.loggers` and there is no `Trainer` to hand them to — tracking goes through `trackers:`, which every backend has, via marainer's plain FUNCTIONS `log_run_context` / `Tracker.log_metrics`, hookup style (1)); no callback protocol; no distributed strategy. Multi-GPU is out of scope ON PURPOSE — that is what Lightning is for, and a half-Trainer here would be a worse one. Ctor knobs the others lack: `device` (a closed `Literal["auto","cpu","cuda","mps"]`; `auto` prefers CUDA -> MPS -> CPU, an explicit value is taken at its word so a CPU-vs-GPU benchmark cannot silently fall back), `checkpoint_dir` (a plain `state_dict` — there is no framework format), `grad_clip`. **It forced a marainer change, and that change is the general rule:** `build_metric_collection`/`scalar_metrics` lived in `marainer.lightning`, whose package `__init__` runs `require("pytorch_lightning")`, so importing them made a deliberately Lightning-free backend need Lightning (measured: `import marainer.lightning.metrics` leaves `pytorch_lightning` in `sys.modules`). They MOVED to `marainer.torch.metrics` — they only ever imported confluid/torch/torchmetrics — with `torchmetrics` moving from marainer's `[lightning]` extra to `[torch]`, and `marainer.lightning` re-exporting all four so no consumer broke (raidar's `from marainer.lightning import scalar_metrics` is untouched). `tests/test_torch_classifier.py::test_it_needs_no_training_framework` AST-scans this module's imports for exactly that regression. **Two loop details that are silent when wrong:** (1) a live (non-`!lazy:`) model reaches `initialize()` with an UNBUILT backbone, because `flow()` fires `solidify()` only when it materializes a deferred spec — the optimizer then dies with *"optimizer got an empty parameter list"* (hit for real with a directly-constructed `TimmModel`), so `initialize()` calls `solidify()` when the model has one; (2) the balanced loss holds its class weights in a BUFFER, so both it and the model are moved to the device, and the injection branches — a `Fluid` loss is FLOWED with `weight=` (a Fluid cannot be mutated in place) while a LIVE one has the attribute SET, because `flow()` on a live object returns it with the runtime kwarg DROPPED (measured: `weight` stayed `None`, i.e. silently unweighted training). **Verified end to end 2026-08-01:** `sonair train --framework torch` on a 256-row MNIST slice with `efficientvit_b0` — LabelMap fitted, loss balanced over 10 classes, train/loss 1.76 with train accuracy 0.471 after ONE epoch, `model.pt` + `class_names.json` + sidecar written. **The val/train gap is BatchNorm, not a bug, and the check is recorded so nobody re-diagnoses it:** with the SAME weights on the SAME data, eval mode (running BN statistics) scored 0.314 while batch-statistic BN scored 0.871 — after 16 optimizer steps the running estimates are still mostly ImageNet's. Every torch backend behaves this way on a short run; do not "fix" the eval pass. Pins: `tests/test_torch_classifier.py` (29).
- **There Is NO `logger:` Slot — `trackers:` Is The Only Output Wiring, And It Is A CONSTRUCTOR Param (2026-08-01):** every backend's `logger` knob is DELETED. It named two different things and neither survived: Lightning's held `pytorch_lightning.loggers.*` (real metric sinks, now replaced by the trackers themselves, adapted through `marainer.lightning.TrackerLogger` in `_build_trainer`), and the other six held framework CALLBACKS under a misleading name. One key, `trackers:`, is now the whole of a run's output wiring on every backend. **The slot MUST be a constructor param annotated `Optional[Union[Tracker, Iterable[Tracker]]]`, and that is not cosmetic:** confluid gates LIST broadcast on the receiving slot's ANNOTATION, so as a post-construction attribute typed `Optional[List[Tracker]]` a `trackers: [...]` key silently did NOTHING — measured, and it meant the entire tracking chain (manifest, provenance, per-epoch metrics) was unreachable from YAML while every unit test passed, because the tests assigned `.trackers` in Python. Do NOT move it back off the constructor, and do NOT narrow the annotation to a bare `List`. **The constructor stores it VERBATIM** (lazy-init mandate): normalizing there would iterate the value, and a deferred `Fluid` is not iterable (`'Class' object is not iterable`). Normalization + flowing happen once in `_live_trackers()`, which writes the result BACK to the slot — one attribute, no `_trackers` shadow copy — because `flow()` on a live object is idempotent but a `Fluid` would be REBUILT on every call, i.e. two MLflow runs for one training run. - **Lazy Backbone — One Cache, Three Triggers (`solidify` / `backbone` / `forward`):** `TimmModel.__init__` does NO functional work (Lazy-Init / Zero-Arg mandate); the timm backbone is built lazily into the **public** submodule `self.classifier` (public name, NOT `_classifier`, so a state_dict round-trips as `classifier.*` through marainer's Lightning checkpoint loader). It builds at most once, triggered by any of: `solidify()` (the build+cache method), the read-only cached `@property backbone` (which just returns `solidify()`), or `forward()` (which routes through `backbone`). **Keep `solidify()` — it's confluid's `flow()`-time build hook** (`flow` never touches `@property` getters — confluid AGENTS rule 3 — so the method hook is what leaves `self.parameters()` ready before `configure_optimizers`, and it's what fires the dual-output StreamStudio node's build-or-warn at node-execute). The `backbone` property is the ergonomic accessor so a **directly-constructed, never-flowed** `TimmModel` still materializes on demand (`model.backbone(x)`). Required config (`model_name` / `num_classes`, sentinels `""`/`0`) is validated at build time with a clear error, never in `__init__`. Do NOT move the build into `__init__` (breaks zero-arg construction) and do NOT drop `solidify()` (breaks flow-time build + the node warning). Pins: `tests/test_timm_classifier.py` (`backbone` property + solidify + checkpoint round-trip).
- **Ergonomic Flat Config via Broadcasting:** `LightningClassifier` exposes ergonomic ctor knobs — `batch_size` / `num_workers` / `max_epochs` / `logger` — so a **flat** YAML drives it purely through Confluid broadcasting (top-level sibling keys inject into the same-named ctor params — no nesting / `!ref`). `batch_size` / `num_workers` are baked into the deferred `DataLoader` stubs (with `recordstream.collate_records`) in `__init__`; `max_epochs` / `logger` are baked into the classifier's OWN `self.lightning = LazyClass(pytorch_lightning.Trainer, max_epochs=…, logger=…)` (there is NO base trainer anymore) — `_build_trainer()`'s `flow(self.lightning)` at run() then materializes any `!class:` logger Fluids in that list. The model is wired `!lazy:sonair.TimmModel` (no `num_classes`); `initialize()` flows it with the dataset-derived count at run time. Gotcha (pinned by `tests/test_classification_trainer.py`): a **list-valued** top-level key (`logger: [...]`) only broadcasts when the receiving param's annotation admits a list — confluid's `_classify_annotation` gates list/dict broadcast on the annotation, so keep `logger` annotated `Optional[Union[Logger, Iterable[Logger], bool]]`. Passing an explicit `train_loader`/`val_loader`/`lightning` overrides the knob-built defaults. Use `pytorch_lightning.loggers.TensorBoardLogger` in flat configs.
- **Task/Role Discovery Tags:** Sonair's classes carry `@configurable(task="classification", role=...)` (which also derives the legacy `category="classification_<role>"`), so navigaitor's `list_classes(task=, role=)` scan + form-spec enumerate them: `TimmModel` → `role="model"`, `LightningClassifier` → `role="trainer"` (its per-task `run()` entry points additionally declare `trainer`/`evaluator`/`predictor` roles via `recordstream.runnable.entrypoint`); the losses (the registered `torch.nn` family) are `role="loss"` and the metrics (the registered `torchmetrics.classification.Multiclass*` AND `Multilabel*` families) are `role="metric"` (see the loss/metric mandate above). Preserve these when adding/renaming — `tests/test_categories.py` pins them, and a dropped tag silently empties the corresponding picker / drops the class from a generated task config.
- **I/O Contract — `trained_model` Output + `Mandatory[...]` Inputs:** `LightningClassifier` declares its confluid I/O contract (the surface StreamStudio / navigaitor read — see confluid's *I/O Contract* mandate). Its constructor input `model` is typed `Mandatory[...]` (the explicit "must be wired" marker, distinct from the defaulted/`Optional` knobs like `train_set`/`test_set`); it declares **three read-only `@output`s DIRECTLY on the class** (not inherited — the old marainer bases are gone): `trained_model` — a read-only `@output` returning the live trained `nn.Module` (`self.model` after `run()`/`initialize()` flowed and trained it) — plus `computed_metrics` (`Dict[str, float]`, final scalar metrics) and `class_names` (`List[str]`). `trained_model` is NOT the `model` *input* (that's the `!lazy:` arch spec) and is NOT a config knob (read-only ⇒ excluded from `to_pydantic`); all three **raise** if accessed while the run hasn't happened (the model still a deferred `Fluid`), so they are run OUTPUTs only. `@output` goes UNDER `@property`. StreamStudio surfaces them as wireable output sockets on the self-running classifier node — `trained_model` on a `RECORDSTREAM_OBJECT:model` socket (docking into a downstream `task: test` classifier's `model` slot), `computed_metrics`/`class_names` on `STRING` (JSON) sockets; navigaitor's form-spec surfaces them under `outputs`. Pins: `tests/test_classification_trainer.py` + `tests/test_classification_evaluator.py` (the `trained_model` / mandatory-input / `computed_metrics` / `class_names` output tests).
