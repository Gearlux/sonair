# sonair — backlog

Open work for this project. Cross-cutting / multi-project initiatives live in the
workspace root `TASKS.md`. Completed items are not archived here — git history is the record.

- [ ] **Decide whether `sonair tensorflow train` needs its own runnable at all** @framework — the `keras` backend (2026-07-29) already runs on TensorFlow: Keras 3 IS `tf.keras` in TF >= 2.16, so `KERAS_BACKEND=tensorflow sonair keras train <cfg>` executes the identical config on TF with no new code. A separate `tensorflow_classifier.py` is only warranted for something Keras 3 does not expose (raw `tf.function`/graph work, SavedModel export specifics, `tf.distribute`). **Installing TF is not free:** `uv pip install --dry-run "tensorflow>=2.16"` (measured 2026-07-29) upgrades protobuf 3.20.3 -> 7.35.1 across 14 dependents INCLUDING mlflow, tensorboard and wandb — marainer's own tracking backends — and downgrades h5py 3.16 -> 3.14, which recordstream stores with. That is the dependency-skew class `AGENTS_MAINTENANCE` warns about, so it needs a deliberate decision (and a full workspace re-verify) rather than an `install` on the way past. @medium
- [ ] **StreamStudio: framework-aware object sockets.** confluid 0.3.0 ships the `framework` axis and navigaitor filters slot options by it, but StreamStudio still lets any `RECORDSTREAM_OBJECT:model` dock into any model slot regardless of engine. Qualifying the socket type (`…:model:torch`) is a BREAKING workflow-format change — ComfyUI enforces socket compatibility by string equality and persists the strings in saved `workflow.json` — so it needs its own decision + a migration story. Until then a canvas can still wire a torch loss into a Keras trainer. See `docs/architecture.md` §2. @medium @architecture
