# Sonair Mandates

- **Adapter, Not Classifier:** Sonair is a thin Confluid-`@configurable` wrapper around `timm`. Any of timm's ~1000 pretrained backbones MUST plug into the **unchanged** `marainer.trainer.LightningTrainer` step flow — no subclassing the Trainer, no overridden step functions, no custom Lightning module.
- **Generic Primitives Live in Marainer / Waivefront / DataFlux — never Sonair:** Reusable predictions sinks do NOT belong in `sonair`. The modality-neutral `ClassificationPredictionsSink` lives in **`marainer`** (`marainer.sinks` — marainer owns the `predictions_sink` contract and the `ClassificationOutput` type it reads, and the sink has zero signal/image coupling); the signal-domain `DetectionPredictionsSink` (pixel→time/frequency back-projection) stays in `waivefront`. Classification needs NO bespoke target op at all — the input is tensorized by the generic `dataflux.ops.torch.ToTensorOp` (after `ConvertToImageOp`) and the label is encoded by the generic `dataflux.ops.target.MetadataToTargetOp` → `EncodeTargetOp` (the declarative scikit-`LabelEncoder` analogue). Sonair stays focused on the model + collate + trainer specialisation.
- **No Loss/Metric Wrappers — Register the Upstream Classes (`sonair.classification`):** Classification losses ARE off-the-shelf `torch.nn` losses and metrics ARE off-the-shelf `torchmetrics.classification` classes; `sonair.classification` `register`s them (no wrapper classes) — the losses (`_CLASSIFICATION_LOSSES`: `CrossEntropyLoss` / `BCELoss` / `BCEWithLogitsLoss` / `MultiLabelSoftMarginLoss` / `MultiMarginLoss` / `MultiLabelMarginLoss` / `SoftMarginLoss` / `HingeEmbeddingLoss`) as `task="classification", role="loss"`, the metrics (`_CLASSIFICATION_METRICS`: the `Multiclass*` family — `MulticlassAccuracy`/`F1Score`/`Precision`/`Recall`/`AUROC`/`AveragePrecision`/`Specificity`/`CohenKappa`/`MatthewsCorrCoef`/`ConfusionMatrix`/`JaccardIndex`/`CalibrationError`/`HammingDistance`) as `task="classification", role="metric"`. Each is pickable in navigaitor's task surfaces, usable from YAML, AND a FluxStudio OBJECT node (`role∈{loss,metric}` is in the bridge `_MEMBER_ROLES`). **They surface in FluxStudio ONLY because `sonair.classification` is its own `confluid.configurables` entry point** (`sonair-classification = "sonair.classification"`) AND every registered class is named in the module's literal `__all__` — `scan_module` filters by `__module__` (which is `torch`/`torchmetrics` for these), so the `__all__`-gated discovery pass is what picks them up. When you add a loss/metric: append it to the right `_CLASSIFICATION_*` tuple AND to `__all__` (`tests/test_categories.py` pins the sync); after changing the set, reinstall the editable (`uv pip install -e ./sonair --no-deps`, or `aisland setup`) so the entry-point metadata refreshes, then restart ComfyUI. Don't reintroduce a sonair loss/metric class that *reimplements* one. Per-class `weight` isn't expressible in YAML (it's a `Tensor`); a future weighted-loss need is met by registering another upstream loss or a generic shim, not by a bespoke sonair wrapper. (This is the model of the redesign: tag/register existing classes; navigaitor scans and generates — it invents nothing.) **The one allowed exception is the "generic shim":** when the upstream loss is a plain *function* rather than an `nn.Module` (so confluid's `register`, which only tags classes, can't reach it), a minimal `nn.Module` wrapper that just stores knobs and delegates in `forward` is permitted — this is a transport shim, not a reimplementation. The reference is `SigmoidFocalLoss` (wrapping `torchvision.ops.sigmoid_focal_loss`): it adds no math, satisfies the zero-arg / lazy-init mandate (ctor only stores `alpha`/`gamma`/`reduction`), and is `@configurable(task="classification", role="loss")`. Like the multi-label family it consumes **float** targets shaped like the logits (one-hot `[N, C]`), not int64 class ids.
- **Collate Discipline:** `sonair.classification.classification_collate_fn` is the **default** DataLoader collate the classification trainer/evaluator wire in (not the generic `marainer.collate.collate_fn_with_metadata`, which *requires* tensor inputs and raises on a PIL image). It **forces each input to an image-like tensor** — PIL/ndarray/tensor → float `[3, H, W]` in `[0,1]`, grayscale expanded to 3 channels (the `TimmModel` is `in_channels=3`) — then stacks to `[N,3,H,W]`, stacks scalar class ids to `[N]` int64, and MUST preserve per-sample metadata as a **list** so string-valued fields (`pack_id`, `iq_file`) survive and sinks can correlate predictions to source samples. **No resize yet:** images in a batch must share spatial dims (`torch.stack`); a clear error names the mismatch. Resize / a model-keyed transform is a deliberate follow-up — don't silently add it here.
- **Trainer/Evaluator Resolve `num_classes` in `initialize()`:** Both call an explicit `initialize()` at the top of `run()` (NOT the auto-fired confluid `solidify` hook — so the dataset walk + model build happen at run time, not when a config is merely materialized). **A concrete (non-`Fluid`) model's classifier head is authoritative — its `num_classes` MUST be read from the model, never derived from a dataset walk that could mis-size the metrics against the head.** The **trainer** resolution order is: a concrete model's `getattr(model, "num_classes")` → explicit trainer arg → the `label_map` (see below) → a lazy model's pinned `num_classes` kwarg → `dataflux.num_classes(train_set)` (walks integer targets, `max+1`); it then `flow(model, num_classes=…)` + flows the metric templates and clones per split. The **evaluator** is **model-driven with NO `num_classes` knob at all**: it flows the model FIRST and reads `num_classes` straight off the LIVE trained model (`getattr(model, "num_classes")`) — there is no evaluator `num_classes` constructor argument to override it, because the trained model's head is the single source of truth (NOT the eval dataset, which may be a subset and would mis-size the metrics; NOT the model's deferred `Fluid` kwargs, filled in later). Both build their per-split metric collections through the shared `marainer.trainer.build_metric_collection(metrics, num_classes=…)` (dict-of-templates → flow+wrap; ready-made `MetricCollection` → as-is) then clone per split (trainer: `train/`·`val/`·`test/`; evaluator: `test/`, idempotently). Use `dataflux.sources.HuggingFaceSource` as the dataset. Do NOT create specialized dataset wrappers in sonair, and do NOT reintroduce `marainer.dimensions` (removed) — flow the classes into instances directly.
- **String Targets Are Auto-Encoded via a `dataflux.LabelMap`; Imbalance Is Auto-Balanced:** `initialize()` peeks the target kind. **Integer targets** flow through unchanged. **String (class-name) targets** are encoded to ids through a `dataflux.LabelMap` (the fittable companion to `EncodeTargetOp`): the pinned `label_map` ctor arg if given, else one **fitted from the train targets** (sklearn `LabelEncoder`, walked with a `tqdm` progress bar). The wired `train`/`val`/`test` sets are then wrapped in a `dataflux.Flux` carrying `label_map.encode_op()`, and the map's `label_names` is exposed on the train set so marainer persists `class_names.json` — which the **evaluator reloads via `LabelMap.load`** (checkpoint-adjacent) so eval/predict share the identical name↔id ordering; **never refit on eval data**. When `balance_classes` is True (default) and the loss accepts a `weight` tensor, the walked targets also yield inverse-frequency class weights injected into `loss_fn` (exposed on `trainer.class_weights`). **`initialize()` walks the train targets AT MOST ONCE** ("Reading targets") and reuses that single pass for ALL of: fitting the encoder, deriving `num_classes` from the data, and computing balance weights — never walk the dataset twice (`_num_classes_without_data()` resolves the count from model/explicit/label_map/lazy-kwarg with no walk, and `_apply_class_weights` consumes the already-walked targets, never re-walking). The name→int map lives in **dataflux** (`LabelMap`, next to `EncodeTargetOp`/`DecodeTargetOp`), NOT sonair — it is a reusable primitive. **Multi-label string targets** (a sequence of names) raise `NotImplementedError` (multi-hot + BCE + collate changes are a TASKS.md follow-up).
- **Backbone Knobs Pass-Through:** `TimmModel.__init__` MUST forward `model_name`, `num_classes`, `pretrained`, and any timm constructor knobs verbatim to `timm.create_model`. Don't shadow names; don't silently rewrite defaults.
- **Lazy Backbone — One Cache, Three Triggers (`solidify` / `backbone` / `forward`):** `TimmModel.__init__` does NO functional work (Lazy-Init / Zero-Arg mandate); the timm backbone is built lazily into the **public** submodule `self.classifier` (public name, NOT `_classifier`, so a state_dict round-trips as `classifier.*` through marainer's Lightning checkpoint loader). It builds at most once, triggered by any of: `solidify()` (the build+cache method), the read-only cached `@property backbone` (which just returns `solidify()`), or `forward()` (which routes through `backbone`). **Keep `solidify()` — it's confluid's `flow()`-time build hook** (`flow` never touches `@property` getters — confluid AGENTS rule 3 — so the method hook is what leaves `self.parameters()` ready before `configure_optimizers`, and it's what fires the dual-output FluxStudio node's build-or-warn at node-execute). The `backbone` property is the ergonomic accessor so a **directly-constructed, never-flowed** `TimmModel` still materializes on demand (`model.backbone(x)`). Required config (`model_name` / `num_classes`, sentinels `""`/`0`) is validated at build time with a clear error, never in `__init__`. Do NOT move the build into `__init__` (breaks zero-arg construction) and do NOT drop `solidify()` (breaks flow-time build + the node warning). Pins: `tests/test_timm_classifier.py` (`backbone` property + solidify + checkpoint round-trip).
- **Ergonomic Flat Config via Broadcasting:** `LightningClassificationTrainer` exposes ergonomic ctor knobs — `batch_size` / `num_workers` / `max_epochs` / `logger` — so a **flat** YAML drives it purely through Confluid broadcasting (top-level sibling keys inject into the same-named ctor params — no nesting / `!ref`). `batch_size` / `num_workers` are baked into the deferred `DataLoader` stubs (with `collate_fn_with_metadata`) in `__init__`; `max_epochs` / `logger` are forwarded to the **base** `LightningTrainer`, which bakes them into `LazyClass(pytorch_lightning.Trainer, max_epochs=…, logger=…)` — the base's `flow(self.lightning)` at run() then materializes any `!class:` logger Fluids in that list. The model is wired `!lazy:sonair.TimmModel` (no `num_classes`); `initialize()` flows it with the dataset-derived count at run time. Gotcha (pinned by `tests/test_classification_trainer.py`): a **list-valued** top-level key (`logger: [...]`) only broadcasts when the receiving param is annotated `List` — confluid's `_classify_annotation` gates list/dict broadcast on the annotation, so keep `logger: List[Any]`. Passing an explicit `train_loader`/`val_loader`/`lightning` overrides the knob-built defaults. Use `pytorch_lightning.loggers.TensorBoardLogger` in flat configs.
- **Task/Role Discovery Tags:** Sonair's classes carry `@configurable(task="classification", role=...)` (which also derives the legacy `category="classification_<role>"`), so navigaitor's `list_classes(task=, role=)` scan + form-spec enumerate them: `TimmModel` → `role="model"`, `LightningClassificationTrainer` → `role="trainer"`, `LightningClassificationEvaluator` → `role="evaluator"`; the losses (the registered `torch.nn` family) are `role="loss"` and the metrics (the registered `torchmetrics.classification.Multiclass*` family) are `role="metric"` (see the loss/metric mandate above). Preserve these when adding/renaming — `tests/test_categories.py` pins them, and a dropped tag silently empties the corresponding picker / drops the class from a generated task config.
- **I/O Contract — `trained_model` Output + `Mandatory[...]` Inputs:** `LightningClassificationTrainer` declares its confluid I/O contract (the surface FluxStudio / navigaitor read — see confluid's *I/O Contract* mandate). Its constructor inputs `model` and `train_set` are typed `Mandatory[...]` (the explicit "must be wired" marker, distinct from the defaulted/`Optional` knobs); its **output** is `trained_model` — a read-only `@property @output` returning the live trained `nn.Module` (`self.model` after `run()`/`initialize()` flowed and trained it). `trained_model` is NOT the `model` *input* (that's the `!lazy:` arch spec) and is NOT a config knob (read-only ⇒ excluded from `to_pydantic`); it **raises** if accessed while the model is still a deferred `Fluid` (pre-run), so it is a run OUTPUT only. `@output` goes UNDER `@property`. FluxStudio renders it as a category-qualified `classification_model` output socket that docks into a downstream evaluator's `model` slot; navigaitor's form-spec surfaces it under `outputs`. Pins: `tests/test_classification_trainer.py` (the `trained_model` / mandatory-inputs tests).
