# Sonair Mandates

## Current state

Image classification on standard Lightning. Three modules — `lightning_classifier.py` (`LightningClassifier`, the merged train/evaluate/test/predict class), `timm_classifier.py` (`TimmModel`, default `efficientvit_b0`), `classification.py` (registered upstream losses/metrics, no wrappers) — plus `cli.py` (`sonair <backend> train/evaluate/predict` — `lightning` implemented, `keras` / `tensorflow` / `jax` / `huggingface` / `mlx` as templates, all in that one file). Datasets are the generic `recordstream.sources.HuggingFaceSource`; batches are **record dicts** addressed by configured keys (`input_key="image"` / `target_key="class"`), collated by `recordstream.collate_records`, labels walked via `iter_key`, string targets encoded by `LabelMap.encode()` (sonair's `encode_stream` is now just that call plus the `label_names` attribute marainer reads off the Stream — a sonair<->marainer handoff, not a dataset concept, which is why only that line stayed); single- AND multi-label (`recordstream.MultiLabel`) targets are both supported, the loss/metric defaults resolving from the data in `initialize()`. Ctor knobs: `batch_size`/`num_workers`/`max_epochs`/`logger` (persistent workers derive from `num_workers` — there is no `persist_workers` knob). Example config: `examples/train_efficientvit_b0_mnist.yaml` — **it trains end to end** (3 epochs MNIST -> 99.5% top-1, verified 2026-07-29). **A classification config MUST carry an image pipeline:** the model is fed by `Stream(source=..., ops=!ref:preprocess)`, where `preprocess` is `ConvertToImage(width/height)` -> `!class:albumentations.Normalize` (the backbone's mean/std) -> `ToTensor(normalize=false)`. Three traps it encodes, each hit for real: (1) a bare `HuggingFaceSource` with no ops hands the model `[N, 28, 28]` and `TimmModel` rejects it — the source does NOT tensorize; (2) the nested source needs the INSTANCE form `!class:...HuggingFaceSource()` **with parens** — without them `Stream.source` stays a deferred Class marker and iteration raises (recordstream's guard names the fix); (3) `ToTensor`'s `normalize` MUST be `false` after an explicit Normalize — `to_tensor`'s heuristic divides any float whose max exceeds 1.0 by 255, so standardized pixels get squashed to ~[-0.01, 0.01] silently. Name `preprocess` once and `!ref:` it from both splits so train and eval cannot drift.

- **The Framework Is A CLI Dimension — `sonair <backend> <verb>` (2026-07-28):** sonair is the workspace DEMO that the config is the program, so the training backend is explicit in the command line. It all lives in `cli.py` — the `lightning` sub-app is written out plainly (three `@script_command`s calling `_dispatch`), and the not-yet-built backends are a `TEMPLATES` dict + a small `_template_app` factory. There is deliberately NO registry module / `Framework` dataclass: for one working backend and a handful of stubs that indirection cost more than it bought (removed 2026-07-28 on review) — if a THIRD real backend lands and the sub-apps start duplicating logic, revisit then, not before. Verbs map `train`/`evaluate`/`predict` -> `fit`/`test`/`predict`, the verb winning over the YAML's `task:`. **The verbs are `flow_mode="manual"` and build through `recordstream.cli.materialize_runnable` (2026-07-29) — NEVER a bare `flow()` / liquifai's `"auto"` deep-flow:** liquifai's DI only materializes a bound node against its document when the command param is annotated with a *configurable class*, and these annotate `runnable: Any` (the runnable is polymorphic), so an auto flow drops EVERY top-level key silently — `train_set` -> `None` (surfacing much later as `could not determine num_classes` after a 0-record target walk) and `max_epochs: 3` -> the ctor default (never surfacing at all). Rationale + the fallbacks: recordstream `AGENTS.md` -> the `recordstream.cli` mandate. Pins: `tests/test_cli_frameworks.py` (`test_dispatch_builds_with_the_flat_configs_top_level_keys` + the delegation spy). Template verbs EXIST (so `--help`/TAB advertise the roadmap), take NO `runnable` param (so they fail before liquifai resolves a config for a missing class), and raise `BackendNotImplementedError` (dual-inherits `LiquifaiError` + `NotImplementedError`, so liquifai renders one clean line + exit 1 instead of a traceback) naming the file to create and the block to replace. Build handlers with a FACTORY, never a default-argument closure — liquifai reads the signature, so smuggled loop variables would surface as `--_name` flags. Every template's name must match a pyproject extra (pinned). Gotcha (RESOLVED 2026-07-29): the message used to be `rich.markup.escape`d at the raise site because liquifai's failure handler interpolated the exception into a Rich markup string — unescaped, `sonair[keras]` lost its extra and printed a WRONG install command. **liquifai 0.1.1 escapes in its own renderer**, so the workaround is GONE; do not reintroduce it (double-escaping would print the literal backslashes). Verified by running `sonair keras train`. **One config, every backend:** the example config keeps engine-agnostic keys (dataset, knobs, run identity) at the TOP LEVEL — which is also the default backend — and each alternative is a `!scope:framework=<name>` block overriding ONLY the framework-specific keys (`runnable`/`model`/`logger`); confluid splices an active block into its parent in document order, last-write-wins. `main()` injects `--scope framework=<verb>` from the backend verb (`_inject_framework_scope`) so the backend is never named twice; an explicit `--scope framework=`/`--framework` always wins. Alternative blocks stay COMMENTED until their runnable class exists — a live block naming a missing class would break `tests/test_examples_load.py`, and until one is uncommented the config declares no `framework` dimension (so the injected scope is an inert no-op, pinned). **Losses/metrics/models/trainers are ENGINE-BOUND — every sonair registration declares `framework="torch"` (2026-07-29):** confluid 0.3.0 added `framework` as a third orthogonal discovery axis (`task`/`role` say what a class is FOR, `framework` says what it can be WIRED TO), so `classification.py`'s losses + metrics, `TimmModel` and `LightningClassifier` all carry it and navigaitor's slot picker filters on it — a torch loss is no longer offered to a Keras trainer. Requires `confluid>=0.3.0` (passing the kwarg against 0.2.0 is a TypeError at import). A future backend registers its OWN set under its own framework; keep each backend's registrations in its own module. NOT yet enforced in StreamStudio — its object sockets are string-equality-matched by ComfyUI and persisted in saved workflows, so qualifying them is a breaking format change (see `TASKS.md`). Rationale: `docs/architecture.md` §2. Pins: `tests/test_cli_frameworks.py` (the CLI axis) + `tests/test_categories.py` (the framework tags). Docs: `docs/frameworks.md`, `docs/architecture.md`.
- **Standard Lightning Classifier + timm Models (2026-07 — supersedes "Adapter, Not Classifier"):** `sonair.lightning_classifier.LightningClassifier` is ONE self-contained standard `pytorch_lightning.LightningModule` — its OWN `training_step`/`validation_step`/`test_step`/`predict_step`/`configure_optimizers` + a `run()` that builds the loaders + `pl.Trainer` and dispatches on a `task` knob (`fit`/`evaluate`/`test`/`predict`, annotated via `recordstream.runnable.entrypoint`) — **`run()` dispatches through `recordstream.runnable.run_entrypoint(self, self.task)`, so those markers ARE the dispatch table; do NOT reintroduce a hand-written `{task: method}` dict** (2026-07-29; rationale + the drift it caused: recordstream `docs/architecture.md` §7). It replaces the old trainer+evaluator PAIR (both subclassed the deleted `marainer` bases). Marainer is now a tracking library — `LightningClassifier` uses it ONLY for optional tracking (`marainer.lightning.TrackingCallback` / `activate_for_lightning`) + torch utils (`marainer.torch.ensure_record_dataset` / `build_metric_collection`); removing marainer needs only a few line changes. `TimmModel` stays a thin `@configurable` timm wrapper. Run via `sonair lightning train/evaluate/predict cfg.yaml` or `recordstream run cfg.yaml` (config roots at `runnable:` + `task:`).
- **Generic Primitives Live in Marainer / Waivefront / RecordStream — never Sonair:** Reusable predictions sinks do NOT belong in `sonair`. The modality-neutral `ClassificationPredictionsSink` lives in **`marainer`** (`marainer.sinks` — marainer owns the `predictions_sink` contract and the `ClassificationOutput` type it reads, and the sink has zero signal/image coupling); the signal-domain `DetectionPredictionsSink` (pixel→time/frequency back-projection) stays in `waivefront`. Classification needs NO bespoke target op at all — the input is tensorized by the generic `recordstream.ops.torch.ToTensor` (after `ConvertToImage`) and the label is encoded by the generic `recordstream.ops.target.EncodeTarget` (the declarative scikit-`LabelEncoder` analogue, fitted and pinned through `recordstream.LabelMap`). Sonair stays focused on the model + collate + trainer specialisation. **Class-imbalance weighting moved out 2026-07-29:** the policy (capability check + inverse-frequency arithmetic + injection) is `marainer.torch.balancing.apply_class_weights`; sonair keeps ONLY the encoding step, which is `LabelMap`-specific. `_apply_class_weights` encodes the walked targets to ids and delegates, REBINDING both `loss_fn` and `class_weights` (a deferred `!class:` loss is flowed with the weights, so the returned object is not the one passed in). Do not reintroduce a private `_loss_accepts_weight` — `tests/test_classification_trainer.py` pins the seam.
- **No Loss/Metric Wrappers — Register the Upstream Classes (`sonair.classification`):** Classification losses ARE off-the-shelf `torch.nn` losses and metrics ARE off-the-shelf `torchmetrics.classification` classes; `sonair.classification` `register`s them (no wrapper classes) — the losses (`_CLASSIFICATION_LOSSES`: `CrossEntropyLoss` / `BCELoss` / `BCEWithLogitsLoss` / `MultiLabelSoftMarginLoss` / `MultiMarginLoss` / `MultiLabelMarginLoss` / `SoftMarginLoss` / `HingeEmbeddingLoss`) as `task="classification", role="loss"`, the metrics (`_CLASSIFICATION_METRICS`: BOTH families — `Multiclass*` (`MulticlassAccuracy`/`F1Score`/`Precision`/`Recall`/`AUROC`/`AveragePrecision`/`Specificity`/`CohenKappa`/`MatthewsCorrCoef`/`ConfusionMatrix`/`JaccardIndex`/`CalibrationError`/`HammingDistance`) sized by `num_classes`, and the multi-label counterparts `Multilabel*` (the same list minus `CohenKappa`/`CalibrationError`, which have no multi-label counterpart, plus `MultilabelExactMatch`, which has no multiclass one) sized by `num_labels` and fed a float multi-hot `[N, C]` target) as `task="classification", role="metric"`. Each is pickable in navigaitor's task surfaces, usable from YAML, AND a StreamStudio OBJECT node (`role∈{loss,metric}` is in the bridge `_MEMBER_ROLES`). **They surface in StreamStudio ONLY because `sonair.classification` is its own `confluid.configurables` entry point** (`sonair-classification = "sonair.classification"`) AND every registered class is named in the module's literal `__all__` — `scan_module` filters by `__module__` (which is `torch`/`torchmetrics` for these), so the `__all__`-gated discovery pass is what picks them up. When you add a loss/metric: append it to the right `_CLASSIFICATION_*` tuple AND to `__all__` (`tests/test_categories.py` pins the sync); after changing the set, reinstall the editable (`uv pip install -e ./sonair --no-deps`, or `aisland setup`) so the entry-point metadata refreshes, then restart ComfyUI. Don't reintroduce a sonair loss/metric class that *reimplements* one. Per-class `weight` isn't expressible in YAML (it's a `Tensor`); a future weighted-loss need is met by registering another upstream loss or a generic shim, not by a bespoke sonair wrapper. (This is the model of the redesign: tag/register existing classes; navigaitor scans and generates — it invents nothing.) **The one allowed exception is the "generic shim":** when the upstream loss is a plain *function* rather than an `nn.Module` (so confluid's `register`, which only tags classes, can't reach it), a minimal `nn.Module` wrapper that just stores knobs and delegates in `forward` is permitted — this is a transport shim, not a reimplementation. The reference is `SigmoidFocalLoss` (wrapping `torchvision.ops.sigmoid_focal_loss`): it adds no math, satisfies the zero-arg / lazy-init mandate (ctor only stores `alpha`/`gamma`/`reduction`), and is `@configurable(task="classification", role="loss", framework="torch")`. Like the multi-label family it consumes **float** targets shaped like the logits (one-hot `[N, C]`), not int64 class ids.
- **Collate Discipline — Wire the Generic `recordstream.collate_records` (record model, 2026-07-25):** `LightningClassifier` wires `recordstream.collate_records` as its DataLoader collate — there is NO bespoke sonair collate. The division of labour: (1) the **config pipeline tensorizes the input** (`ConvertToImage` → `ToTensor`), so at collate time each record's `input_key` value (default key `image`) is already a `[3, H, W]` `Image`; (2) `collate_records` **stacks** the `Image` value to `[N, 3, H, W]` and gathers plain entries as per-record lists; (3) the model boundary reads the batch back through recordstream's GENERIC readers — `batch_tensor(batch, key, device)` for the input and `batch_metadata(batch, exclude=(input_key, target_key))` for the per-record metadata a predictions sink needs (sonair's private `_batch_input`/`_batch_metadata` were DELETED 2026-07-29 and moved to `recordstream.batch`, where deltaid had an independent duplicate — do not reintroduce them); and the target comes from recordstream too — `_batch_target` was DELETED 2026-07-29 once `batch_tensor` grew a `dtype=` parameter and `multi_hot` moved down. What remains is `LightningClassifier._targets(batch)`, a two-branch CHOICE, not a shaper: `multi_hot(...)` -> `torch.as_tensor` for multi-label, else `batch_tensor(..., dtype=torch.int64)` — int64 named EXPLICITLY because a dataset yielding int32 label tensors is legal and `CrossEntropyLoss` rejects it (*"expected scalar type Long but found Int"*); the old code relied on `LabelMap` happening to emit Python ints. Do not reintroduce a sonair-side shaper: if a new task shape is needed, it is a recordstream primitive plus a branch here. The record keys are CONFIG, not convention: `LightningClassifier(input_key="image", target_key="class")` (the `HuggingFaceSource` defaults). Don't reintroduce a sonair collate or move input-forcing back into the collate (resize / a model-keyed transform remains a pipeline concern).
- **`LightningClassifier` Resolves `num_classes` in `initialize()`:** The single `LightningClassifier` calls an explicit `initialize()` at the top of each `run()` entry point (NOT the auto-fired confluid `solidify` hook — so the dataset walk + model build happen at run time, not when a config is merely materialized). **A concrete (non-`Fluid`) model's classifier head is authoritative — its `num_classes` MUST be read from the model, never derived from a dataset walk that could mis-size the metrics against the head.** For **`task="fit"`** the resolution order is: a concrete model's `getattr(model, "num_classes")` → explicit `num_classes` ctor arg → the `label_map` (see below) → a lazy model's pinned `num_classes` kwarg → `recordstream.num_classes(train_set)` (walks integer targets, `max+1`); it then `flow(model, num_classes=…)` + flows the metric templates and clones per split. For **`task="evaluate"`/`"test"`/`"predict"`** it is **model-driven**: it flows/loads the model FIRST and reads `num_classes` straight off the LIVE model (`getattr(model, "num_classes")`) — the trained model's head is the single source of truth (NOT the eval dataset, which may be a subset and would mis-size the metrics; NOT the model's deferred `Fluid` kwargs, filled in later). It builds per-split metric collections through `marainer.lightning.build_metric_collection(metrics, num_classes=…)` (dict-of-templates → flow+wrap; ready-made `MetricCollection` → as-is) then clones per split (`train/`·`val/`·`test/` for fit; `val/` or `test/` for the eval tasks, idempotently). Use `recordstream.sources.HuggingFaceSource` as the dataset. Do NOT create specialized dataset wrappers in sonair, and do NOT reintroduce `marainer.dimensions` (removed) — flow the classes into instances directly.
- **String Targets Are Auto-Encoded via a `recordstream.LabelMap`; Imbalance Is Auto-Balanced:** `initialize()` peeks the FIRST target and asks recordstream's rule — `is_class_id(value)` — instead of sniffing types itself (the old `detect_target_kind` / `_target_to_int` are DELETED 2026-07-29; do not reintroduce them). Encoding goes through `LabelMap.to_ids`, which passes already-encoded ids through, so there is no name-vs-id branch left. A multi-label target is a `recordstream.MultiLabel` item (`iter_key` unwraps it to a LIST) — a sequence from the peek therefore IS multi-label, decided by the item type rather than by guessing what a list might mean. **Integer targets** flow through unchanged. **String (class-name) targets** are encoded to ids through a `recordstream.LabelMap` (the fittable companion to `EncodeTarget`): the pinned `label_map` ctor arg if given, else one **fitted from the train targets** (deterministic sorted-unique ordering, walked with a `tqdm` progress bar — sklearn was dropped from recordstream 2026-07-29). The wired `train`/`val`/`test` sets are then wrapped in a `recordstream.Stream` carrying `label_map.encode_op()`, and the map's `label_names` is exposed on the train set so marainer persists `class_names.json` — which the **evaluator reloads via `LabelMap.load`** (checkpoint-adjacent) so eval/predict share the identical name↔id ordering; **never refit on eval data**. When `balance_classes` is True (default) and the loss accepts a `weight` tensor, the walked targets also yield inverse-frequency class weights injected into `loss_fn` (exposed on `trainer.class_weights`). **`initialize()` walks the train targets AT MOST ONCE** ("Reading targets") and reuses that single pass for ALL of: fitting the encoder, deriving `num_classes` from the data, and computing balance weights — never walk the dataset twice (`_num_classes_without_data()` resolves the count from model/explicit/label_map/lazy-kwarg with no walk, and `_apply_class_weights` consumes the already-walked targets, never re-walking). The name→int map lives in **recordstream** (`LabelMap`, next to `EncodeTarget`/`DecodeTarget`), NOT sonair — it is a reusable primitive. **Multi-label targets are SUPPORTED (2026-07-29)** — a `MultiLabel` needs no config: `initialize()` sets `self.multilabel` from the peek and everything downstream follows from that ONE flag — `_batch_target(..., multilabel=True)` builds an `[N, C]` float multi-hot instead of `[N]` int64 ids, `_resolve_task_defaults()` picks `BCEWithLogitsLoss` + the `Multilabel*` metrics, `_metric_dims()` sizes them by `num_labels` instead of `num_classes`, and balancing flattens each record's ids through `LabelMap.to_ids` so a two-label record counts for both classes. Class-name strings encode exactly as in the single-label case (`LabelMap.fit` takes a `MultiLabel` directly). Do NOT add a `multilabel:` config knob — the target's item type already says it, and a knob could disagree with the data. Only the PREDICT-side sink is still single-label (top-k; see `TASKS.md`). Pins: the multi-label group in `tests/test_classification_trainer.py` (incl. an end-to-end `run()`).
- **`predict_step` Emits the CONTRACT, and `_write_predictions` Slices It Per Record (2026-07-29):** `predict_step` returns a `marainer.outputs.ClassificationOutput` built by `marainer.torch.outputs.classification_output(logits)` — NOT the raw logits tensor. A predictions sink reads `probs` / `class_idx` by name and cannot softmax on the caller's behalf (only the model knows whether its head already did). Returning raw logits was a real defect: `ClassificationPredictionsSink.write` does `prediction.get("probs")`, so a wired sink died with `AttributeError: 'Tensor' object has no attribute 'get'` on the first batch. `test_step` passes the same contract to the sink while its metrics still consume the raw logits. Separately, `_write_predictions` SLICES the batched output row-wise via `_per_record_predictions` — the sink contract is per-record while the model emits `[N, C]`, and the old list-wrapping wrote ONE entry for an N-record batch. `_per_record_predictions` handles, in order: a list (already per-record), a `{"predictions": [...]}` wrapper, a batched mapping with agreeing lengths (sliced), anything else (one prediction). Pins: `tests/test_predictions.py` (incl. an end-to-end pass through the real `marainer.sinks` sink).
- **Task-Shaped Defaults Are SENTINELS, Resolved in `initialize()` (2026-07-29):** `loss_fn` and `metrics` default to **`None`** — meaning *not chosen*, never *no loss*. `_resolve_task_defaults()` fills an unset slot once `initialize()` knows `self.multilabel` (`BCEWithLogitsLoss` + `Multilabel*` vs `CrossEntropyLoss` + `Multiclass*`) and is idempotent, so an explicitly wired loss/metric is NEVER replaced. A live default in the constructor signature is prohibited: it makes "the user chose CrossEntropy" indistinguishable from "the user said nothing", so a multi-label run would either silently train with the wrong loss or silently discard a deliberate choice. Two ordering constraints, both already violated once: (1) resolution must run BEFORE the balancing probe in `_initialize_fit` — `loss_accepts_weight(None)` answers "cannot be balanced" and silently skips the target walk; (2) `training_step`/`validation_step` call `_resolve_task_defaults()` themselves so a directly-invoked step (tests, a custom loop) works without `initialize()`. Rationale: `docs/architecture.md` §3. Pins: `tests/test_classification_trainer.py` (`test_loss_fn_defaults_to_cross_entropy`, `test_an_explicitly_wired_loss_is_never_replaced`) + `tests/test_classification_evaluator.py`.
- **Deferred Slots Are Declared `Lazy[T]`, Never `Any` Or A Hand-Written Union (2026-07-29):** a slot this class flows ITSELF at run time — `model` (flowed with `num_classes=`), `train_set`/`test_set`, and the body slots `optimizer` (`params=`), `train_loader`/`val_loader`/`test_loader` (`dataset=`), `lightning` — MUST be annotated `Lazy[T]` (composed as `Mandatory[Lazy[T]]` where required). Two spellings are PROHIBITED: (a) `Optional[Union[X, Fluid]]`, which hand-writes confluid's alias — `Lazy = Annotated[Union[T, Fluid], _LAZY_MARKER]` — and silently drops the marker; (b) a bare `Any`, which type-checks nothing. What the marker buys differs by slot kind and the difference is REAL: for CONSTRUCTOR params it is machine-read (`confluid.lazy_param_names` reports them; liquifai's auto deep-flow SKIPS them instead of eagerly building a target that needs a runtime kwarg), while for BODY slots `lazy_param_names` scans `__init__` params only, so the marker is inert there and deferral is enforced by the slot holding a `LazyClass` value — the annotation still earns its place by giving `to_pydantic` a real type for navigaitor's form-spec / StreamStudio widgets. Before this landed, `lazy_param_names(<this class>)` returned an EMPTY set while the code flowed those very slots by hand. Dataset slots use the shared `marainer.torch.RecordSource` alias (`Dataset | Iterable[Record]` — the contract `ensure_record_dataset` enforces), never a locally-invented union. Follow-up filed in confluid TASKS: teach `lazy_param_names` to scan body slots the way `to_pydantic` already does.
- **Backbone Knobs Pass-Through:** `TimmModel.__init__` MUST forward `model_name`, `num_classes`, `pretrained`, and any timm constructor knobs verbatim to `timm.create_model`. Don't shadow names; don't silently rewrite defaults.
- **Lazy Backbone — One Cache, Three Triggers (`solidify` / `backbone` / `forward`):** `TimmModel.__init__` does NO functional work (Lazy-Init / Zero-Arg mandate); the timm backbone is built lazily into the **public** submodule `self.classifier` (public name, NOT `_classifier`, so a state_dict round-trips as `classifier.*` through marainer's Lightning checkpoint loader). It builds at most once, triggered by any of: `solidify()` (the build+cache method), the read-only cached `@property backbone` (which just returns `solidify()`), or `forward()` (which routes through `backbone`). **Keep `solidify()` — it's confluid's `flow()`-time build hook** (`flow` never touches `@property` getters — confluid AGENTS rule 3 — so the method hook is what leaves `self.parameters()` ready before `configure_optimizers`, and it's what fires the dual-output StreamStudio node's build-or-warn at node-execute). The `backbone` property is the ergonomic accessor so a **directly-constructed, never-flowed** `TimmModel` still materializes on demand (`model.backbone(x)`). Required config (`model_name` / `num_classes`, sentinels `""`/`0`) is validated at build time with a clear error, never in `__init__`. Do NOT move the build into `__init__` (breaks zero-arg construction) and do NOT drop `solidify()` (breaks flow-time build + the node warning). Pins: `tests/test_timm_classifier.py` (`backbone` property + solidify + checkpoint round-trip).
- **Ergonomic Flat Config via Broadcasting:** `LightningClassifier` exposes ergonomic ctor knobs — `batch_size` / `num_workers` / `max_epochs` / `logger` — so a **flat** YAML drives it purely through Confluid broadcasting (top-level sibling keys inject into the same-named ctor params — no nesting / `!ref`). `batch_size` / `num_workers` are baked into the deferred `DataLoader` stubs (with `recordstream.collate_records`) in `__init__`; `max_epochs` / `logger` are baked into the classifier's OWN `self.lightning = LazyClass(pytorch_lightning.Trainer, max_epochs=…, logger=…)` (there is NO base trainer anymore) — `_build_trainer()`'s `flow(self.lightning)` at run() then materializes any `!class:` logger Fluids in that list. The model is wired `!lazy:sonair.TimmModel` (no `num_classes`); `initialize()` flows it with the dataset-derived count at run time. Gotcha (pinned by `tests/test_classification_trainer.py`): a **list-valued** top-level key (`logger: [...]`) only broadcasts when the receiving param's annotation admits a list — confluid's `_classify_annotation` gates list/dict broadcast on the annotation, so keep `logger` annotated `Optional[Union[Logger, Iterable[Logger], bool]]`. Passing an explicit `train_loader`/`val_loader`/`lightning` overrides the knob-built defaults. Use `pytorch_lightning.loggers.TensorBoardLogger` in flat configs.
- **Task/Role Discovery Tags:** Sonair's classes carry `@configurable(task="classification", role=...)` (which also derives the legacy `category="classification_<role>"`), so navigaitor's `list_classes(task=, role=)` scan + form-spec enumerate them: `TimmModel` → `role="model"`, `LightningClassifier` → `role="trainer"` (its per-task `run()` entry points additionally declare `trainer`/`evaluator`/`predictor` roles via `recordstream.runnable.entrypoint`); the losses (the registered `torch.nn` family) are `role="loss"` and the metrics (the registered `torchmetrics.classification.Multiclass*` AND `Multilabel*` families) are `role="metric"` (see the loss/metric mandate above). Preserve these when adding/renaming — `tests/test_categories.py` pins them, and a dropped tag silently empties the corresponding picker / drops the class from a generated task config.
- **I/O Contract — `trained_model` Output + `Mandatory[...]` Inputs:** `LightningClassifier` declares its confluid I/O contract (the surface StreamStudio / navigaitor read — see confluid's *I/O Contract* mandate). Its constructor input `model` is typed `Mandatory[...]` (the explicit "must be wired" marker, distinct from the defaulted/`Optional` knobs like `train_set`/`test_set`); it declares **three read-only `@output`s DIRECTLY on the class** (not inherited — the old marainer bases are gone): `trained_model` — a read-only `@output` returning the live trained `nn.Module` (`self.model` after `run()`/`initialize()` flowed and trained it) — plus `computed_metrics` (`Dict[str, float]`, final scalar metrics) and `label_names` (`List[str]`). `trained_model` is NOT the `model` *input* (that's the `!lazy:` arch spec) and is NOT a config knob (read-only ⇒ excluded from `to_pydantic`); all three **raise** if accessed while the run hasn't happened (the model still a deferred `Fluid`), so they are run OUTPUTs only. `@output` goes UNDER `@property`. StreamStudio surfaces them as wireable output sockets on the self-running classifier node — `trained_model` on a `RECORDSTREAM_OBJECT:model` socket (docking into a downstream `task: test` classifier's `model` slot), `computed_metrics`/`label_names` on `STRING` (JSON) sockets; navigaitor's form-spec surfaces them under `outputs`. Pins: `tests/test_classification_trainer.py` + `tests/test_classification_evaluator.py` (the `trained_model` / mandatory-input / `computed_metrics` / `label_names` output tests).
