workspace root `TASKS.md`. Completed items are not archived here — git history is the record.

- [ ] **Extract the engine-neutral half of `initialize()` — AFTER raidar and deltaid** @medium @refactor @blocked — the target peek -> multilabel flag -> `LabelMap` fit/encode -> `num_classes` -> `class_names` sequence now exists in SIX near-identical copies: `LightningClassifier`, `TorchClassifier`, `KerasClassifier`, `TensorFlowClassifier` (which stopped INHERITING it on 2026-08-01), `FastaiClassifier` and the jax/mlx pair. None of it is engine-specific. **Deliberately deferred (user instruction 2026-08-01):** the base is to be designed against classification AND detection, so it waits until raidar and deltaid have been through the same treatment — extracting it now would fit it to classification six times over and then need reshaping for a detector's targets, boxes and metrics. Until then the copies are held together by BEHAVIOURAL drift tests (`test_the_duplicated_classification_half_agrees_with_the_keras_backend`, `test_the_loss_and_metric_defaults_match_the_lightning_backend`) rather than by a base class; a change to the label handling has to be made in each backend and those tests will say so. When it happens, it must NOT reintroduce `TensorFlowClassifier` as a `KerasClassifier` subclass — that relationship was retired for a reason (five overrides that never called `super()`, plus a narrowed precondition; see AGENTS.md).
- [ ] **The other six backends have no non-scalar-metric path** @low @parity — `keras` / `tensorflow` / `fastai` / `jax` / `mlx` / `huggingface` each resolve their own metric sets, and none of them can consume a `torchmetrics` confusion matrix or report one of their own; they also have no per-split metric slots (a Keras `compile()` takes ONE metric list for the whole run), which is why the example's keras block nulls both metric keys. The reporting seam now EXISTS on the marainer side (`Tracker.log_text` + `render_matrix_as_table`), so what is left per backend is a confusion metric its engine can compute plus the same "compute, split, render" call — but that is still six copies of it, so it waits on the engine-neutral base above.
- [ ] **A confusion matrix as a FIGURE, not only a table** @low @cross-project — `Tracker.log_text` gives the rendered table a home in every backend, which is readable but not glanceable; `torchmetrics`' own `metric.plot()` returns a matplotlib figure that `Tracker.log_figure` already accepts. The cost is that matplotlib becomes a runtime dependency of an eval epoch rather than an optional import, so it should be a knob (off by default) rather than a replacement — the table costs nothing and works where no figure can be rendered.
- [ ] **`marainer.fastai` tracking callback** @medium @cross-project — every other backend forwards PER-EPOCH metrics to marainer trackers (`marainer.lightning.TrackingCallback`, `marainer.keras.keras_tracking_callback`); the fastai backend currently writes only the end-of-run artifacts (`save_class_names` + `write_metrics_sidecar`) and passes wired fastai `Callback`s through the `logger:` slot. The missing piece is a `fastai.callback.core.Callback` that forwards `learn.recorder` values, and it belongs in **marainer**, not sonair (the "generic primitives live upstream" mandate) — so it is a marainer task with a one-line sonair follow-up in `_callbacks()`.
