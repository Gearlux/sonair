# Sonair Mandates

- **Adapter, Not Classifier:** Sonair is a thin Confluid-`@configurable` wrapper around `timm`. Any of timm's ~1000 pretrained backbones MUST plug into the **unchanged** `marainer.trainer.LightningTrainer` step flow — no subclassing the Trainer, no overridden step functions, no custom Lightning module.
- **Generic Primitives Live in Marainer / Waivefront / DataFlux — never Sonair:** Reusable predictions sinks do NOT belong in `sonair`. The modality-neutral `ClassificationPredictionsSink` lives in **`marainer`** (`marainer.sinks` — marainer owns the `predictions_sink` contract and the `ClassificationOutput` type it reads, and the sink has zero signal/image coupling); the signal-domain `DetectionPredictionsSink` (pixel→time/frequency back-projection) stays in `waivefront`. Classification needs NO bespoke target op at all — the input is tensorized by the generic `dataflux.ops.torch.ToTensorOp` (after `ConvertToImageOp`) and the label is encoded by the generic `dataflux.ops.target.MetadataToTargetOp` → `EncodeTargetOp` (the declarative scikit-`LabelEncoder` analogue). Sonair stays focused on the model + collate + trainer specialisation.
- **No Loss Wrapper — Register the Upstream Loss:** The classification loss IS `torch.nn.CrossEntropyLoss`; `sonair.classification` `register`s it (no wrapper class) as the `task="classification", role="loss"` configurable, so it's pickable in navigaitor's task surfaces and usable from YAML (`label_smoothing` / `ignore_index` / `reduction`). Don't reintroduce a sonair loss class. Per-class `weight` isn't expressible in YAML (it's a `Tensor`); a future weighted-loss need is met by registering another upstream loss or a generic shim, not by a sonair wrapper. (This is the model of the redesign: tag/register existing classes; navigaitor scans and generates — it invents nothing.)
- **Collate Discipline:** `classification_collate_fn` MUST preserve per-sample metadata alongside the batched input/target tensors so sinks can correlate predictions back to source samples.
- **Trainer Derives `num_classes` from Any Dataset:** The trainer's `_dataset_num_classes()` helper reads `num_classes()` method or `derived_dimensions()["num_classes"]` from any dataset, so configs may OMIT `num_classes` entirely — it will be derived at run time. Use `dataflux.sources.HuggingFaceSource` as the dataset; it yields dataflux Samples that marainer can introspect. Do NOT create specialized dataset wrappers in sonair.
- **Backbone Knobs Pass-Through:** `TimmModel.__init__` MUST forward `model_name`, `num_classes`, `pretrained`, and any timm constructor knobs verbatim to `timm.create_model`. Don't shadow names; don't silently rewrite defaults.
- **Ergonomic Flat Config via Broadcasting:** `LightningClassificationTrainer` exposes ergonomic knobs — `batch_size` / `num_workers` / `persist_workers` / `max_epochs` / `logger` — that BUILD the DataLoaders (with `classification_collate_fn`) + the `pytorch_lightning.Trainer`, so a **flat** YAML drives it purely through Confluid broadcasting (top-level sibling keys inject into the same-named trainer ctor params — no nesting / `!ref`). The model is wired `!lazy:sonair.TimmModel` (no `num_classes`) so the dataset-derived count is injected at run time. Two gotchas, both pinned by `tests/test_classification_trainer.py`: (1) a **list-valued** top-level key (`logger: [...]`) only broadcasts when the receiving param is annotated `List` (`logger: Optional[List[Any]]`) — confluid's `_classify_annotation` gates list/dict broadcast on the annotation, so keep the annotation; (2) `flow()` does NOT recurse into a list-valued kwarg of a deferred `Class`, so the trainer **pre-flows the leaf logger Fluids** before folding them into `Class(L.Trainer, logger=[...])` — else Lightning gets raw Fluids. Passing an explicit `train_loader`/`val_loader`/`lightning` overrides the knob-built defaults. Use `pytorch_lightning.loggers.TensorBoardLogger` in flat configs; `marainer.loggers.MarainerTensorBoardLogger` currently can't be flowed standalone (its `(*args, **kwargs)` signature defeats confluid's kwarg filtering — known gap).
- **Task/Role Discovery Tags:** Sonair's classes carry `@configurable(task="classification", role=...)` (which also derives the legacy `category="classification_<role>"`), so navigaitor's `list_classes(task=, role=)` scan + form-spec enumerate them: `TimmModel` → `role="model"`, `LightningClassificationTrainer` → `role="trainer"`, `LightningClassificationEvaluator` → `role="evaluator"`; the loss is `torch.nn.CrossEntropyLoss` `register`-ed as `role="loss"`. Preserve these when adding/renaming — `tests/test_categories.py` pins them, and a dropped tag silently empties the corresponding picker / drops the class from a generated task config.
